### 1. 보스 AI

**DecideState: 거리 + 각도로 패턴 고르기**
- `Pattern`에 `minDistance / maxDistance / minAngle / maxAngle`
- 각도 = `Vector3.SignedAngle(보스 forward, 플레이어 방향(평면), Vector3.up)` → -180 ~ 180, **+ = 보스 오른쪽**
- `GetInfo(out distance, out angle)` 한 곳에서 계산. `IsInRange`는 private
- `CanAttack()`은 매개변수 없음. Chase는 "공격 가능한지"만 묻고, **결정은 전부 DecideState**에서
- 같은 패턴 2연속 금지: `lastState` 기억 → `patternList`(조건 맞음) → `tempPatternList`(지난번과 다름) → 비면 `patternList`로 연속 허용

**상태 추가**
| 파일 | 내용 |
|---|---|
| `RoarState` | 발견 프레임에 Idle → Roar. SpreadFire 클립, 끝나면 Decide |
| `MeleeAttack` (abstract, 전 `ClawAttack`) | `HitboxOn` 전까지 `RotateTowards`로 플레이어 추적. 애니 이벤트 parameter = `BossHitbox.id`인 히트박스만 켜고 끔 |
| `ClawAttackLeft / Right / ClawCombo / Bite / JumpBite` | `MeleeAttack` 자식. Bite는 제자리 클립이라 앞으로 안 나감(그냥 둠) |
| `TurnLeftState / TurnRightState` | Turn90 RM 클립, 끝나면 Decide. 등 뒤에 있을 때 제자리 돌기 |

**BossStates.Update**: `animator.IsInTransition(0)`이면 return. 같은 상태 재진입 때 이전 애니 정보를 읽는 문제 때문.

**규칙 (애니메이터 ↔ 코드)**
- 상태 컴포넌트 Exit Time < 애니메이터 "돌아가는 화살표" Exit Time. 안 지키면 상태에 갇힘
- 트리거 이름 = 코드 `AnimatorTrigger` / 애니메이터 칸 이름 = 인스펙터 Animator State Name / 오브젝트 이름은 자유
- 돌아가는 화살표는 "끝나고 코드가 트리거 없는 상태(Idle)로 갈 때만" 필요 (할퀴기·물기). Walk/Roar/Turn/Death는 불필요

**설계 결정 (GDD 미반영)**
- 간보기(Strafe) 안 함: 대검 차지를 하려면 보스가 멈춰 있는 틈이 필요
- 앞발 내려찍기 삭제: 할퀴기와 모션이 같아 헷갈림
- 1단계 공격은 전부 가드 가능
- 피로 상태: 앞발 공격 하다가 자빠짐

#### 고민한 것과 트레이드오프

**1. 각도 필드 모양**
| 선택지 | 장점 | 단점 |
|---|---|---|
| A) `maxAngle` 하나 (정면 기준 좌우 대칭) | 단순 | "등 뒤에서만" 같은 패턴을 표현 못 함 |
| **B) `minAngle` + `maxAngle`** ✅ | 거리와 같은 모양. 120~180처럼 뒤쪽 전용 패턴(꼬리치기)도 가능 | 필드 두 개 |

**2. Chase와 Decide의 "공격 가능" 기준 맞추기**
- 각도 필터를 넣자 `CanAttack(distance)`는 거리만 봐서, 사거리 안 등 뒤에 서면 Chase → Decide(후보 0개) → Chase가 매 프레임 반복됨.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A) `CanAttack(distance, angle)` — Chase가 계산해서 넘김 | 받은 숫자만 보니 시험하기 쉬움. Chase가 거리를 따로 쓸 일(멀면 뛰기)이 생기면 자연스러움 | "어떻게 재나"가 Chase·Decide 두 곳에 생김. 한쪽만 바꾸면 기준이 또 어긋남 |
| **B) `CanAttack()` — DecideState가 직접 계산** ✅ | 재는 방법과 판단이 한 파일에만. "결정은 전부 Decide" | Chase에서 거리·각도를 직접 못 봄 |
- A와 B 사이에서 흔들렸음. 기준: 방금 겪은 무한 반복이 바로 "기준이 두 곳에 있어서" 생긴 버그였다는 것.

**3. 겹치는 범위 검사를 어디로 모을까**
| 선택지 | 장점 | 단점 |
|---|---|---|
| **A) 패턴 하나를 검사하는 함수** ✅ | Enter와 CanAttack이 같은 조건을 씀 | foreach는 각자 남음 |
| B) 후보 목록을 돌려주는 함수 | foreach까지 하나로 | Chase가 매 프레임 리스트를 새로 만듦 |
- 함수 자리: `Pattern.IsInRange()`(카드가 스스로 답함) vs **DecideState의 private `IsInRange(pattern, …)`** ✅. Pattern은 값만 담는 상자로 두고 판단은 Decide가 함 → 2번 결정과 결이 맞음.

**4. 거리·각도 계산 모으기**
| 선택지 | 장점 | 단점 |
|---|---|---|
| A) `GetDistance()`, `GetAngle()` 두 개 | 단순 | 두 번 호출 |
| **B) `GetInfo(out distance, out angle)`** ✅ | 한 번 호출로 둘 다 | `out` 문법 |
| C) CanAttack이 구한 값을 필드에 저장하고 Enter가 재사용 | 계산 한 번 | Idle → Decide로 들어오면 **예전 값**이 남아 틀린 판단 |
- "모으기"는 계산을 한 번만 하는 게 아니라 **계산 코드를 한 곳에만 쓰는 것**.

**5. 왼쪽 / 오른쪽 구분**
- 옆발 할퀴기(보스 오른쪽 = 왼발, 보스 왼쪽 = 오른발, 정면 = 양발 콤보)를 넣으려고 `Vector3.Angle`(0~180, 좌우 구분 없음) → `Vector3.SignedAngle(…, Vector3.up)`(-180~180)으로 바꿈. 좌우 기준은 **보스 기준**.

**6. 옆구리에 붙으면 보스가 뺑글뺑글 도는 문제**
| 선택지 | 장점 | 단점 |
|---|---|---|
| A) 제자리 돌기 상태 (Turn90 RM 클립) | 도는 동작 자체가 공격 틈 (몬헌) | 상태·애니메이터 칸 추가, 좌우 고르기 필요 |
| B) 루트모션 없는 Walk + 코드로 이동 | "가까우면 멈추고 회전만"이 쉬움 | 발이 미끄러져 보임. 이동 코드 새로 |
| C) 옆발 할퀴기부터 | 옆구리 문제 대부분 해결 | 등 뒤는 남음 |
| D) 옆걸음(Strafe)으로 궤도 돌기 | 전진하지 않아서 플레이어를 지나치지 않음 | 사실상 간보기 행동 (7번) |
- 결론: **C + A** (옆은 옆발, 뒤는 제자리 돌기). GDD의 "옆·뒤에 붙으면 몸을 돌리며 할퀴기"와 같은 방향.
- `rotateSpeed`만 올리는 것도 해 봤지만 계속 돎 (어려웠던 개념 "걷기 + 회전 = 원").

**7. 간보기(Strafe)를 넣을까 — 패턴 느낌 정하기**
- 처음엔 "어떤 요소가 플레이어를 더 만족시킬까"로 보다가, **"이 보스 행동이 플레이어에게 무엇을 하게 만드나"**로 기준을 바꿈.

| 보스 행동 | 플레이어가 하게 되는 것 |
|---|---|
| 옆·뒤는 안전 (회전이 느림) | 위치를 잡고 파고들어 차지 |
| 옆에 오래 붙으면 회전 + 옆발 할퀴기 | 계속 붙지 않고 읽음. 태클·상쇄로 받아침 |
| 간보기 (옆걸음) | 기다리거나 다가감. 보스가 계속 움직여서 **차지가 어려움** |
| 거리 벌리기 (백스텝 + 불) | 붙어 있으면 손해라는 걸 배움 |
- 대검은 보스가 멈춘 틈에 차지해야 함 → **간보기 없음**. 간보기를 Decide 목록에 넣을지 Idle 확률로 할지, 도는 방향을 랜덤 / 플레이어 위치 / 플레이어 이동 방향(다크소울식) 중 무엇으로 할지도 고민했지만 함께 접음.

**8. 발견하고도 3초 기다리는 문제**
| 선택지 | 장점 | 단점 |
|---|---|---|
| A) 발견한 프레임에 바로 Decide | 가장 단순 | 연출 없음 |
| B) 발견 직후용 대기 시간을 따로 | 조절 가능 | 필드 추가 |
| **C) 포효 상태 (RoarState)** ✅ | "알아챘다"를 보여 줌 (몬헌) | 상태 추가. 포효 클립이 없어 SpreadFire 재사용 → 브레스와 시작 동작이 같아 헷갈릴 수 있음 (사운드·속도로 구분 예정) |
- 포효 뒤에는 브레스·점프 물기로 잇고 싶었지만 아직 상태가 없어서 **Roar → Decide** ✅. Roar에 다음 패턴 목록을 직접 두는 안은 거리·각도를 안 봐서 보류 (③ 후속타 분기 때 다시).
- 포효 `exitTime`: 미리보기에서 포효가 끝나고 자세가 돌아오기 시작하는 지점(88%) → 0.88.

**9. 각도 경계**
- 경계선 두 개(a = 정면/옆, b = 옆/뒤)만 정하면 다섯 패턴이 정해짐. 처음 a = 50, b = 90.

| 패턴 | 각도 |
|---|---|
| 콤보 | -50 ~ 50 |
| 왼발 | 50 ~ 90 |
| 오른발 | -90 ~ -50 |
| TurnRight | 90 ~ 180 |
| TurnLeft | -180 ~ -90 |
- 옆(40°)이 정면(100°)보다 좁은 게 걸림. 폭 계산: 정면 = `2a`, 옆 하나 = `b - a`. a를 줄이면 콤보 범위가, b를 늘리면 등 뒤가 좁아짐.
- 옆발을 40부터로 하고 싶음. 콤보를 -40~40으로 맞출지, -50~50으로 겹쳐 둘지(겹친 곳은 랜덤)는 **보류**.
- 범위 사이에 **구멍이 생기면** 후보 0개 → Chase → 뺑글뺑글. 경계는 맞닿거나 겹치게.
- "불편하지 않은 값"의 기준: ① 보이는 것과 맞는가(발이 실제로 닿는 범위), ② 안전지대 넓이(난이도). 차지할 틈을 위해 등 뒤는 넉넉하게.

**10. 범위를 어떻게 잴까**
- 할퀴기는 HitboxOn 전까지 추적 회전 → **Decide가 보는 각도 ≠ 실제로 맞는 각도**. 실제 범위 ≈ 클립이 쓸고 가는 범위 + 예비동작 동안 돈 각도(`rotationSpeed × HitboxOn까지 시간`).

| 선택지 | 장점 | 단점 |
|---|---|---|
| 한 패턴씩 각도를 바꿔 가며 맞는지 기록 | 정확. 추적 회전까지 포함 | 거리 × 각도마다 결과가 달라 끝이 없음 |
| **대략 넣고 이상한 순간만 고치기** ✅ | 빠름 | 정밀하지 않음 → 11/01 손맛 때 다듬기 |
- 서 있는 자리의 각도를 보려고 임시 OnGUI에 각도 표시 추가.

**11. Turn 거리**

**15. 히트박스를 id로 고르기**

**16. 같은 Turn이 연달아 나올 때**
- Can Transition To Self가 꺼져 있으면 애니가 다시 시작하지 않음 → 클립 끝 프레임에 멈춘 채 코드만 반복.
- 켜도 블렌드(0.25초) 동안 이전 Turn 정보(이미 exitTime을 넘음)를 읽어 바로 끝난 걸로 착각 → `BossStates.Update`에 `IsInTransition` 가드 ✅. 대가: "컴포넌트 Exit Time < 돌아가는 화살표 Exit Time" 규칙을 꼭 지켜야 함.

**17. 이름 짝을 어느 쪽에 맞출까 (Turn, Bite)**
- 트리거와 칸 이름이 다를 때 코드를 고칠지 애니메이터를 고칠지 → **애니메이터 칸 이름을 트리거와 같게** (`TurnRight`, `Bite`, `JumpBite`). 트리거·칸·인스펙터 이름이 같으면 짝을 헷갈릴 일이 줄어듦.

#### 어려웠던 개념

| 개념 | 헷갈린 점 | 정리 |
|---|---|---|
| `Vector3.Angle` vs Quaternion | Chase는 `FlatRotationTo`(Quaternion)를 쓰는데 Decide는 왜 `Vector3.Angle`? | Chase는 실제로 **돌려야** 해서 목표 회전값이 필요. Decide는 min/max와 비교할 **숫자 하나**면 됨 |
| `Vector3.Angle` 범위 | 최대 90이면 정면 90° 안? | 좌우 구분이 없어서 0~90 = 왼쪽 90° + 오른쪽 90° = **앞쪽 반원 전체** |
| `SignedAngle`의 축 | Z축 아닌가? | 축 = 꽂고 도는 막대. 바닥에서 좌우로 트는 건 **Y(`Vector3.up`)**. Z로 돌면 옆으로 구름 |
| `CanAttack` vs `IsInRange` | 같은 함수 아닌가 | IsInRange = 카드 **한 장** 검사, CanAttack = 손패 **전체** 중 한 장이라도 되나 |
| 거리·각도를 두 번 계산 | 한 번 구해서 다 넘기면 안 되나 | Decide로 오는 길이 둘(Idle, Chase). Idle 길에는 미리 구한 값이 없음. 같은 프레임 두 번 계산은 비용 거의 없음 |
| `ChangeState` 다음 줄 | 부르면 바로 Exit로 끝나는 줄 앎 | 평범한 함수 호출이라 끝나면 **다음 줄로 돌아옴**. `SetActive(false)`도 이번 Update를 끊지 않음 → 바꾼 뒤 `return` |
| `exitTime` | 정확히 뭔지 | 직접 만든 필드. 애니 `normalizedTime`(재생 비율 0~1)이 넘으면 `OnAnimationEnd`. 미리보기 % = 이 값. Loop 클립은 1, 2, 3…으로 계속 커짐 |
| enum 추가 위치 | — | 인스펙터의 enum은 **숫자 순서**로 저장 → 중간에 넣으면 저장된 값이 밀림. 항상 맨 끝에. 필드 기본값은 0번(`IdleState`) |
| 프리팹 Original / Variant / 씬 | Variant를 고쳤는데 씬이 안 바뀜 | Original → Variant → 씬 순서로 물려받고 **아래 단계에서 덮어쓴 값이 이김**. 굵은 글씨 + 파란 줄 = 오버라이드, 오른쪽 클릭 Revert로 지움 |
| 이름 세 종류 | 인스펙터 Animator State Name에 트리거 이름을 넣음 | 트리거 = 코드 `AnimatorTrigger`, 칸 이름 = Animator State Name, 오브젝트 이름은 자유 |
| 걷기 + 회전 = 원 | `rotateSpeed`를 올려도 계속 돎 | 전진하면서 돌면 원을 그림(회전 반경 ≈ 걷는 속도 ÷ 회전 속도). 원 안쪽 옆구리는 정면으로 못 들어옴 |
| 추적 회전과 범위 | 클립이 닿는 만큼 범위를 어떻게 잡나 | HitboxOn 전까지 돌기 때문에 판단 각도와 맞는 각도가 다름 |
| Hurtbox와 Hitbox 자리 | 턱뼈에 이미 Hurtbox가 있는데 어디에? | 같은 오브젝트면 히트박스를 끌 때(`SetActive`) Hurtbox도 꺼짐 → 턱뼈 밑 **형제** 오브젝트(같은 부모, 같은 들여쓰기)로 |
| 상속이 어색함 | 물기가 ClawAttack을 상속? | 하는 일은 근접 공격 공통이라 맞음. 어색한 건 **이름** → MeleeAttack |
| 목록 하나 더 | `patternList`를 새로 만들라는 건지 | `patternList`는 그대로 두고 `tempPatternList`를 **하나 더**. 지난번과 다른 것만 모으고, 비면 원래 목록에서 뽑음 |

### 2. 플레이어 피격 모션

#### 전체 흐름

| 순서 | 어디서 | 무슨 일 |
|---|---|---|
| 1 | 보스 히트박스 인스펙터 | 히트박스마다 `Reaction`(Small / Big / KnockDown)을 고름 |
| 2 | `BossHitbox.OnTriggerEnter` | 플레이어에 닿으면 `new AttackInfo(damage, fatigue, pos, reaction)` |
| 3 | `PlayerHealth.TakeDamage` | 무적이면 무시 → 체력 깎음 → 죽으면 `Die` 후 return → 아니면 `Reaction` int 설정 + `Hit` 트리거 |
| 4 | 애니메이터 Any State | `Hit` + `Reaction == 0/1/2` → Small / Big / KnockDown |

넉다운은 6~7 사이에 KnockDown → Down(누워 있기 루프) → StandUp(일어나기)를 거치고, 그동안 무적입니다.

#### 고민한 것과 트레이드오프

결정마다 어떤 선택지가 있었고, 무엇을 얻고 무엇을 포기했는지 정리합니다.

**1. 반응 종류를 애니메이터에 어떻게 넘길까**
| 선택지 | 장점 | 단점 |
|---|---|---|
| 트리거 3개 (반응마다 하나) | 화살표 조건이 트리거 하나로 단순 | 파라미터가 반응 수만큼 늘어남. 코드에서 반응별로 분기해야 함 |
| **트리거 1개 + int 1개** ✅ | 파라미터 2개로 고정. enum을 `(int)`로 그대로 넘겨서 코드에 분기가 없음 | 화살표마다 조건이 2개 (Hit + Reaction == n). enum 순서를 바꾸면 애니메이터 조건도 같이 바꿔야 함 |

**2. Big 피격 중에 또 Big을 맞으면 (Can Transition To Self)**
- Small은 바로 정함: 연타 맞으면 계속 움찔하는 게 자연스러움 → 켜기.
- **Big은 애매했음.** 켜면 연타 공격(양발 콤보 등)에 맞을 때마다 휘청임이 처음부터 다시 나오고, 끄면 두 번째 타격은 데미지만 들어가서 "맞았는데 안 맞은 것처럼" 보임.
- 기준을 몬헌에서 가져옴: 새 타격이 앞의 반응을 덮어씀 → **켜기**. 대가로 연타에 갇힐 수 있는데, 그건 회피기(구르기)로 빠져나오는 구조로 받아들임.
- KnockDown은 켜도 꺼도 문제가 있었음 (켜면 누워서 또 쓰러짐, 끄면 트리거가 남아 일어나자마자 또 쓰러짐). 화살표 설정으로 풀 문제가 아니라 **"쓰러져 있을 때 맞으면?"이라는 설계 문제**라고 보고 **넉다운 무적**으로 해결.

**3. Transition Duration**
- 0이면 반응은 즉각이지만 자세가 툭 끊겨 튐. 길면 부드럽지만 "맞았다"는 느낌이 늦게 옴.
- Any State에서 오는 화살표는 앞 모션이 매번 달라서, 비율이 아니라 **Fixed Duration(초)**으로 정함. 일단 0.2초, 손맛 볼 때 다시 조정.

**4. 넉다운을 한 칸으로 할까, 세 칸으로 나눌까**
- 클립이 쓰러짐 / 누워 있기(Loop) / 일어나기로 나뉘어 있어서 **세 칸 다 씀**. 대가로 "누워 있다가 언제 일어나는가"를 따로 정해야 했음.

**5. 언제 일어날까**
| 선택지 | 장점 | 단점 |
|---|---|---|
| A) 애니메이터 Exit Time만 | 코드 필요 없음 | 플레이어가 개입할 수 없음 |
| B) 코드가 시간 재기 | 시간을 인스펙터에서 조절 | 역시 플레이어가 개입할 수 없음 |
| C) 입력으로 일어나기 | 몬헌처럼 빨리 일어나기 가능 | 입력을 안 하면 영원히 누워 있음 |
| **C + 자동 기상** ✅ | 둘의 장점을 합침 | 화살표 2개 (트리거 / Exit Time 3) + 트리거가 남지 않게 하는 조건이 필요 |
- 자동 기상 시간은 루프 1 / 2 / 3바퀴 중 **3바퀴**.
- 입력은 이동 / 구르기 / 둘 다 중 **둘 다**.

**6. 일어나기 클립**
- 같은 시리즈의 구르며 일어나기(`KnockDown_Front_BW/FW_Rolling_StandUp`)와 다른 폴더의 그냥 일어나기(`Damage_Front_Down_StandUp`) 중 **그냥 일어나기**를 고름.
- 대가: 시리즈가 달라서 시작 자세나 import 설정이 안 맞을 위험이 있었음 → 실제로 Root Y 설정 문제가 생겼고, 세 클립 import 설정을 통일해서 해결 (트러블슈팅 4, 5).

**7. 맞는 순간 이동을 바로 끊을까, 감속할까 (`StopMovement(true / false)`)**
- 몬헌·다크소울은 패드로만 해 봐서 감각으로는 판단이 안 됐음 → 레퍼런스 동작을 기준으로 정함.
- 몬헌·다크소울은 **입력 이동은 즉시 끊기고, 밀려나는 건 피격 모션이 함** → `true`.
- 대가: 지금은 클립의 XZ 루트 모션을 버리고 있어서(`OnAnimatorMove`는 구르기만 적용) **제자리에서 맞음**. 밀려나기는 손맛 단계로 미룸.

**8. 넉다운 무적을 어떻게 구분할까**
| 선택지 | 장점 | 단점 |
|---|---|---|
| A) 칸 이름으로 (`IsName`) | 애니메이터를 안 건드림. 파일이 안 늘어남 | 칸 이름이 코드에 박힘. HitState 하나가 두 역할을 함 |
| **B) Tag 분리 + KnockDownState** ✅ | 역할이 깔끔: HitState = 움찔, KnockDownState = 무적 + 일어나기 | 파일 하나 추가. 애니메이터 Tag를 바꿔야 함 |
- B를 골랐지만 KnockDownState 안에서 "Down 칸일 때만 입력 받기"는 결국 `IsName("Down")`을 씀. Tag로 큰 구분을 하고, 세부 구분은 칸 이름으로 하는 절충.

**9. 보스 공격이 안 닿음: 용 크기를 줄일까, 거리를 줄일까**
| 선택지 | 장점 | 단점 |
|---|---|---|
| A) 용 크기 + 패턴 거리 같이 줄이기 | 화면에서 보스가 덜 가림 | 패턴 거리·`discoverDistance`를 전부 다시 맞춰야 함. 크기만 줄이면 오히려 더 헛침 |
| B) 크기 그대로, 패턴 `maxDistance`만 줄이기 | 숫자만 고치면 됨 | 보스가 더 가까이 붙어서 공격함 |
- **결정 보류**. 피격 모션을 먼저 끝내기로 함.

**10. 테스트 방법**
- 인스펙터 ContextMenu(Test Player Hit)는 누르는 순간 Game 뷰 포커스가 빠져서 **달리면서 테스트할 수 없음**.
- 보스한테 맞아서 테스트하려 했지만 공격이 안 닿음 (9번).
- → **임시 키(1 / 2 / 3)**로 반응별 피격을 직접 발생시킴. 데미지는 0으로 해서 여러 번 눌러도 안 죽게 함. 테스트 후 삭제.

**11. 마우스 감도**
- 패드로만 해 봐서 마우스 기준이 없었음 → **"손목 한 번에 90~180도"**라는 동작 기준을 정하고, 보스 주위를 돌면서 보스를 화면 가운데에 둘 수 있는지로 맞춤.

**12. 피격 모션 개수**
| 선택지 | 장점 | 단점 |
|---|---|---|
| A) Small 하나 | 가장 빠름 | 모든 피격이 같은 모션 |
| B) 피해량으로 Small / Big | 큰 공격이 달라 보임 | 트리거나 칸이 늘어남 |
| **C) Small / Big / KnockDown** ✅ | 큰 공격에는 넘어짐 | 일어나는 동안 무방비 시간까지 정해야 함 (→ 4, 5, 8번) |

**13. 반응 종류를 누가 정할까**
| 선택지 | 장점 | 단점 |
|---|---|---|
| A) 피해량으로 (`PlayerHealth`가 정함) | 보스 쪽 코드는 그대로 | 방어구로 피해가 줄면 같은 공격인데 모션이 바뀜 |
| **B) 공격 쪽에서 (`BossHitbox` 인스펙터)** ✅ | 패턴마다 고정(할퀴기 Small, 물기 Big). GDD 구현 메모의 "`AttackInfo`에 태그 필요"와 같은 자리라 가드 불가·화염 태그도 나중에 붙일 수 있음 | `AttackInfo` 생성자가 바뀜 → 기본값으로 다른 호출부는 그대로 |
- enum 이름: `HitState`는 곧 만들 피격 상태 클래스(`DodgeState`, `DrinkState`처럼) 이름과 겹쳐서 **`HitReaction`**.

#### 어려웠던 개념

| 개념 | 헷갈린 점 | 정리 |
|---|---|---|
| `SetInteger(해시, 값)` | 인자가 하나뿐이면 에러, 순서를 바꾸면 에러 없이 무시 | 첫 번째 = **어느 파라미터**, 두 번째 = **무슨 값**. 둘 다 int라 컴파일러가 못 잡음 |
| 이름 비슷한 해시 두 개 | `HitHash`(Trigger)와 `ReactionHash`(Int)를 서로 바꿔 씀 | 해시 이름 = 애니메이터 파라미터 이름. 파라미터 **타입**이 맞는지 같이 확인 |
| 트리거가 안 꺼짐 | 버그인 줄 알았음 | 트리거는 **화살표가 가져갈 때** 꺼짐. 가져갈 화살표가 없으면 켜진 채 남음 |
| Sub-State Machine의 Entry 화살표 | 지울 수 없음 | 묶음의 기본 칸 표시. Any State에서 칸으로 바로 가면 안 거침 |
| Transition Duration | 뭐였는지 기억 안 남 | 앞 모션과 새 모션을 **섞는 시간**. Fixed Duration이면 초 단위 |
| Root Transform 설정 | 같은 시리즈 클립인데 튀고, 뜨고, 바닥을 뚫음 | Bake 안 하면 움직임이 루트 모션으로 빠지는데, 이 프로젝트는 구르기 외에 루트 모션을 버림 → 회전·높이는 **Bake + Original** |
| 용 크기와 거리 | 용이 커서 안 맞는다고 생각함 | 크기는 콜라이더·루트 모션과 같이 줄지만, 패턴 거리 같은 **월드 숫자는 안 줄어듦** |

#### 트러블슈팅

1. **`SetInteger` 인자 순서를 바꿔도 컴파일됨**
   `SetInteger(해시, 값)`인데 둘 다 int라 바꿔 써도 에러가 없음 → 없는 파라미터에 값을 넣어 아무 일도 안 일어남. 해시 이름(`HitHash`/`ReactionHash`)도 서로 바뀌어 있었음. **조용히 무시되는 버그**라 눈으로 확인해야 함.

2. **트리거가 안 꺼짐**
   트리거는 **그 트리거를 조건으로 쓰는 화살표가 넘어갈 때** 꺼짐. 화살표가 없으면 켜진 채로 남음. 반대로, 쓸 때가 아닌데 걸어 두면 나중에 엉뚱한 순간 발동함("남은 쪽지" 문제). → KnockDownState는 **Down 칸일 때만** `StandUp`을 걸게 함 (`stateInfo.IsName("Down")`). 일어나는 중에 걸면 다음 넉다운 때 눕자마자 일어나 버림.

3. **Sub-State Machine의 Entry → Small 화살표가 안 지워짐**
   묶음의 기본 칸(주황색) 표시라 지울 수 없음. Any State에서 칸으로 **바로** 꽂으면 Entry를 안 거쳐서 영향 없음.

4. **KnockDown → Down에서 몸이 튐 (회전)**
   Loop Time을 켜면서 Loop 클립의 import 설정이 기본값(Root Rotation = Body Orientation, Bake 꺼짐)으로 생김. 누워 있으면 "몸통 방향"이 위나 옆을 가리켜서 Unity가 몸을 돌려 맞춤. → 세 클립 모두 Rotation **Bake + Original**로 통일.

5. **KnockDown은 공중에 뜨고, StandUp은 다리가 바닥을 뚫음 (높이)**
   Root Position Y를 Bake 안 하면 위아래 움직임이 루트 모션으로 빠짐. 그런데 `PlayerController.OnAnimatorMove`는 **구르기일 때만** `deltaPosition`을 적용하고 나머지는 버림 → 쓰러지며 내려가는 움직임 / 일어나며 올라가는 움직임이 사라짐. → Y **Bake + Original**.

6. **보스 공격이 안 맞음**
   레이어는 정상 (히트박스 mask = PlayerHurtbox, 플레이어 레이어 = PlayerHurtbox, 충돌 매트릭스 켜짐). 일시정지 후 Scene 뷰로 보니 히트박스가 "닿을락 말락" → **휘두르기 시작 거리(패턴 maxDistance)가 용 팔 길이보다 멂**. 용 크기를 줄여도 패턴 거리·`discoverDistance`는 월드 값이라 같이 안 줄어듦 → 줄이면 오히려 더 헛침. **미해결 (나중에)**.

7. **애니메이터를 파일(YAML)로 고칠 때 주의**
   Unity에서 저장 안 한 애니메이터 변경이 있으면, 파일을 바꾸는 순간 Unity가 다시 읽으면서 그 변경이 날아갈 수 있음 → 저장 안 된 상태에서는 에디터 스크립트(Unity 안에서 열린 에셋을 직접 수정)로 작업.

#### 기타
- 마우스 감도: 기준 = 손목 한 번에 90~180도. 세로는 가로보다 조금 낮게. 플레이 모드에서 바꾼 값은 꺼지면 원래대로 돌아감.
- 테스트용 임시 1/2/3 키 → 테스트 후 `Update`는 삭제함.

**10. 판정이 불과 같이 뻗게**
- 캡슐은 켜지는 순간 전체 길이가 판정 → 불이 닿기 전 먼 곳에서 맞음.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **코드로 캡슐 늘리기** ✅ | 불과 매끄럽게 맞음 | 코드 추가 |
| 히트박스 여러 개를 이벤트로 차례대로 | 코드 없음 | 히트박스마다 HashSet이 따로 → 2~3번 맞음 |
- 단위: **속도(m/s)** ✅ (파티클 Start Speed와 같은 단위) vs 시간(몇 초 만에).
- 시작 시점: `HitboxOn`부터 vs **`Flame` 켜질 때부터 + `Enter`에서 0** ✅ → 캡슐이 **보이는 불**을 따라가서 `HitboxOn` time과 상관없이 길이가 맞음.

**11. 잔상**
- `Stop()` 뒤 남는 불 = Start Lifetime. 줄이면 불 길이도 줄어듦 (길이 ≈ 속도 × 수명) → **Lifetime ↓ + Speed ↑**. 판정은 `HitboxOff`에서 바로 꺼지니까 잔상이 짧을수록 보이는 불 ≈ 맞는 범위.

**12. 중간에 끊겼을 때 / 피로 상태**
- 피로는 이미 "공격 끝나고" 적용됨 (`Exhausted()`는 표시만, `IdleState`가 Decide를 막음). 그래도 죽음·상쇄 휘청·부위 파괴 경직은 공격을 끊음 → **`Exit`에서 이펙트 끄기** ✅ (누가 끊든 한 곳에서).

**13. 테스트 방법**
- Decide 패턴에 바로 넣기 vs **임시 B 키** ✅ (원할 때 바로 봄. 나중에 지움).
- 불티가 보이는지 Game 뷰로 볼 때: 임시로 Play On Awake 켜고, 용이 안 움직이게 `IdleState` Discover Distance = 0 → 끝나고 둘 다 되돌림 (씬 Discover Distance는 원래 **50**으로 오버라이드돼 있음, 프리팹은 100).

| 선택지 | 장점 | 단점 |
|---|---|---|
| A) Shooting 이펙트 + `OnParticleCollision` | 보이는 것 = 판정, 폭발 자동 | 파티클 충돌은 기본으로 트리거와 안 부딪힘. 쏜 뒤 제어 불가. 히트박스 구조와 따로 놂 |
| **B) 투사체 오브젝트 직접** ✅ | 히트박스 구조 그대로. 속도·사거리·유도를 정할 수 있음 | 스크립트·프리팹 새로 |

**2. 걷기만 해도 피해짐**
- 쏘는 순간 위치를 노려서, 도착까지(거리 15 ÷ 속도 20 ≈ 0.75초) 걸어간 거리 > 불덩이 반지름이면 빗나감.

| 선택지 | 장점 | 단점 |
|---|---|---|
| 크기 키우기 | 값만 | 피할 수 없는 공처럼 보임 |
| 속도 올리기 | 걸을 시간 감소 | 안 보임 |
| 예측 조준 | 걸으면 맞고 방향 틀면 피함 | 플레이어 속도 읽기 |
| **약한 유도** ✅ | 걸어서는 잘 못 피함 | 피하는 법이 읽기 어려울 수 있음 → 값 작게 (30°/s, 3초에 최대 90°) |
| **폭발 범위** ✅ | 빗나가도 근처면 맞음 | 폭발 판정 필요 |
- 기준: "걷기로는 안 되고 **행동(구르기)**을 해야 피해지는" 쪽 (GDD: 예비동작을 보고 대응을 고른다). 몬헌 리오레우스 = 빠른 직선 + 착탄 폭발.

**3. 직격 + 폭발이면 두 번 맞음**

| 선택지 | 장점 | 단점 |
|---|---|---|
| A) 피해는 폭발에서만 (`OverlapSphere` 코드) | 한 번, 단순 | `BossHitbox`와 별개 피해 코드 |
| B) 직격 + 폭발 따로 | 직격이 더 아픔 | 두 번 맞음 (모션도 두 번) |
| **C) 폭발을 `BossHitbox` 프리팹으로, 투사체에선 `BossHitbox` 뺌** ✅ | 한 번. "판정은 BossHitbox"(브레스와 같은 기준) | 프리팹 하나 더 |
- 리오레우스처럼 직격이든 폭발이든 **한 번**.

### 1. 작은 정리: 불덩이 회전 멈추기, 보스가 공격 뒤 멈추는 버그

시작 커밋: `ea4f86f0 화염 브레스 및 불덩이 패턴`.

요약: 불덩이를 쏜 뒤에도 플레이어 쪽으로 계속 돌던 것을 **`RotateOff` 애니 이벤트**로 멈춤. 테스트 중 **Bite 뒤에 보스가 `BiteState`에 갇히는 버그**를 찾아, 상태 Exit Time과 화살표 Exit Time 사이 간격을 벌려서 고침 (JumpBite·FireBall도 같이).

#### 전체 흐름 (불덩이)

| 순서 | time | 회전 |
|---|---|---|
| `Enter` | 0 | 켬 |
| `Shoot` | 0.442 | 불덩이 생성 (조준은 `Shoot()`이 플레이어 위치로 따로) |
| `RotateOff` | 0.443 | **끔** → 후딜 동안 방향 고정 |
| 상태 Exit Time | 0.7 | `OnAnimationEnd` → Idle |

#### 코드

| 파일 | 변경 | 이유 / 메모 |
|---|---|---|
| `States/Attack.cs` | `ReceiveAnimEvent`에 `RotateOff` → `isRotating = false` | `HitboxOn`이 없는 공격(불덩이)도 회전을 멈출 수 있게. `Attack`에 있어서 다른 공격도 씀 |

#### 에디터

- `DragonBoss.controller` → `FireBall` 칸 `AnimStateEventSender`: `RotateOff 0.443` 추가 (parameter 없음)
- Variant 상태 Exit Time: `Bite` 0.8 → **0.7**, `JumpBite` 0.8 → **0.75**, `FireBall` 0.74 → **0.7**
- `FireBallState` 오브젝트: 씬에만 추가돼 있던 것 → **Variant로 옮김** (Apply). `shootPoint`도 Variant 안의 입 오브젝트를 가리킴

#### 고민한 것과 트레이드오프

**1. 불덩이 회전을 어떻게 끌까**
| 선택지 | 장점 | 단점 |
|---|---|---|
| **A) 회전 끄는 애니 이벤트 추가** ✅ | `Attack`이 받으니 다른 공격도 씀. time만 바꿔 시점 조절 | 이벤트 하나 더 |
| B) `Shoot()`에서 끄기 | 이벤트 추가 없음 | `isRotating`이 private → 끄는 통로 필요. 시점이 쏘는 순간 고정 |
- 이름: `TurnOffRotate` → **`RotateOff`** ✅ (`HitboxOff`, `EffectOff`처럼 대상 + Off 순서).
- 시점: 불을 다 쏜 뒤 → `Shoot`(0.442) 바로 뒤 **0.443** ✅.

**2. 상태가 끝을 못 알아채는 버그 고치기**
| 선택지 | 장점 | 단점 |
|---|---|---|
| **A) 값으로 간격 벌리기** (Variant 상태 Exit Time ↓) ✅ | 코드 안 고침 | 상태마다 따로. 나중에 값 다듬다 간격이 좁아지면 또 생김 |
| B) `BossStates.Update` 검사 바꾸기 ("내 칸에 들어갔다가 다른 칸으로 넘어갔으면 끝") | 모든 상태 해결 | "한 번 들어갔는지" bool 필요 (`Enter` 직후엔 애니메이터가 아직 이전 칸) |
- 간격 기준: Bite처럼 0.1 정도면 프레임이 튀어도 충분. 상태 Exit Time을 낮추면 그만큼 일찍 Decide → 다음 공격의 Any State 화살표가 클립 끝을 끊을 수 있음 (테스트 때 확인).

#### 어려웠던 개념

| 개념 | 헷갈린 점 | 정리 |
|---|---|---|
| 쏜 뒤 회전을 왜 끄나 | 정면에서 테스트하면 이질감이 없음 | ① 후딜 동안 계속 따라 돌면 옆·뒤로 파고들 빈틈이 없음 (리오레우스는 불덩이 뒤 방향 고정) ② 끝날 때 늘 정면이라 다음 Decide에서 옆발·Turn이 잘 안 나옴. 근접 공격은 `HitboxOn`에서 이미 꺼짐 |
| 상태 끝 검사가 "가끔" 실패 | 왜 가끔만 멈추나 | `BossStates.Update`는 **전환 중이 아님 + 아직 내 칸**일 때만 Exit Time을 봄. 상태 Exit Time ~ 화살표 Exit Time 사이가 유일한 기회 → 그 구간이 1프레임쯤이면 프레임이 조금만 길어도 건너뜀 → 애니메이터는 Idle인데 상태는 계속 `BiteState` |

#### 트러블슈팅

1. **Bite 뒤 보스가 멈춤** — OnGUI에 `BiteState`가 계속 떠 있음. 상태 Exit Time 0.8, 화살표 0.8125, 클립 40프레임(약 1.33초) → 간격 약 0.017초 = 60fps 1프레임. 같은 위험: JumpBite(0.8 / 0.8125), FireBall(0.74 / 0.75, 30프레임 → 1프레임 미만). 세 상태 Exit Time을 낮춤.

| 상태 | 상태 Exit Time | 화살표 Exit Time | 간격 (대략) |
|---|---|---|---|
| Bite | 0.7 | 0.8125 | 9프레임 |
| JumpBite | 0.75 | 0.8125 | 5프레임 |
| FireBall | 0.7 | 0.75 | 3프레임 |
| 할퀴기 L/R | 0.8 | 0.85 | 넉넉 |
| 콤보 | 0.8 | 0.906 | 넉넉 |
| 브레스 | 0.9 | 0.925 | 느린 재생이라 넉넉 |

### 3. 작은 정리: 불덩이 꼬리가 한 번에 사라짐

요약: 터질 때 `Destroy(gameObject)`가 자식 파티클까지 지워서 World 꼬리가 뚝 끊겼음 → **이펙트 `Stop()` + 오브젝트는 늦게 지우기**.

#### 전체 흐름 (터질 때)

| 순서 | 어디서 | 무슨 일 |
|---|---|---|
| 1 | `OnTriggerEnter` / 수명 끝 | `Explode()` → `isExploded = true` |
| 2 | `Explode` | 폭발 이펙트·히트박스 생성 (그대로) + `fireballEffect.Stop()` → 새 입자만 멈춤 |
| 3 | `FixedUpdate` | `isExploded`면 `return` → 그 자리에 멈춤 |
| 4 | `effectFadeTime`(3초) 동안 | 남은 입자가 수명만큼 서서히 사라짐. 다시 불린 `Explode`는 `isExploded`로 막힘 |
| 5 | 3초 뒤 | `Destroy(gameObject, effectFadeTime)`로 삭제 |

#### 코드

| 파일 | 변경 | 이유 / 메모 |
|---|---|---|
| `Boss/FireBallProjectile.cs` | 필드 `fireballEffect`(ParticleSystem), `effectFadeTime`(3) | 3 = `FX_Fireball_01` 입자 수명 중 가장 긴 값. 짧으면 다시 뚝 끊김 |
| | `FixedUpdate` 첫 줄 `if (isExploded) return;` | 늦게 지우는 동안 계속 날아가지 않게 |
| | `Explode`: `Destroy(gameObject)` → `Stop()` + `Destroy(gameObject, effectFadeTime)` | |

#### 에디터

- `FIreBall` 투사체 프리팹: `Fireball Effect` = **프리팹 모드 Hierarchy의 자식** `FX_Fireball_01`

#### 고민한 것과 트레이드오프

| 선택지 | 장점 | 단점 |
|---|---|---|
| A) 이펙트를 떼어 내기 (`SetParent(null)` → `Stop()` → 나중에 삭제) | 본체는 바로 삭제 | 이펙트 오브젝트를 따로 지워야 함 |
| **B) 불덩이를 늦게 지우기** ✅ | `Destroy` 한 줄에 지연만 | 그동안 이동·충돌을 `isExploded`로 막아야 함 |

#### 어려웠던 개념

| 개념 | 헷갈린 점 | 정리 |
|---|---|---|
| 부모 `Destroy` | — | 부모를 지우면 자식도 같이 지워짐 → 파티클 시스템이 없어지니 수명이 남은 입자도 함께 사라짐. 서서히 사라지려면 **파티클 시스템이 살아 있어야** 함 (브레스 때의 `Stop()` 정리와 같음) |
| 프리팹 안 참조 | 꽂았는데 안 멈춤 | Project 창의 원본 에셋을 꽂으면 `Instantiate`해도 **원본을 계속 가리킴** → `Stop()`이 원본에 불림. 프리팹 **안**의 오브젝트를 꽂아야 복제본의 자식으로 바뀜. 파일에서 참조에 다른 에셋의 `guid`가 붙어 있으면 바깥 참조 |

#### 트러블슈팅

1. **꽂았는데 불덩이가 3초 동안 계속 타다 사라짐** — `Fireball Effect`에 Project 창의 `FX_Fireball_01` 원본을 끌어다 놓음 → 프리팹 모드 Hierarchy의 자식으로 다시 꽂음.

### 4. 작은 정리: 발견 전 Idle = 두리번거리기

요약: 애니메이터 기본 칸을 `IdleLookAround`로 바꿈. 코드 변경 없음.

| **A) 루프 먼저** ✅ (금 가중치 → 토 부위파괴·보상·소울 + 패턴 값 → 일 대장간·요리 + 피로·상쇄 → 월 2단계·가드·태클·화염 → 화 마무리) | 자르면 안 되는 것이 앞. 밀리면 전투 쪽이 잘림 | 보스 전투를 중간에 끊고 루프로 갔다가 월요일에 다시 돌아옴 |
| B) 전투 먼저 | 하던 보스 전투를 이어서 끝냄 | 밀리면 대장간·2단계(루프)가 위험 |

| 헷갈린 점 | 정리 |
|---|---|
| 패턴 조건·히트박스를 안 고쳤는데 가중치·후속타를 먼저 해도 되나 | 됨. Decide는 **① 조건(거리·각도)으로 후보 거르기 → ② 후보 중에서 고르기**. 가중치는 ②에 붙는 규칙이라 ①의 값이 주말에 바뀌어도 그대로 씀. 히트박스는 고르기와 상관없음. 단, 가중치를 줄 상황에 **후보가 있어야** 효과가 있음 (예: 각도 구멍 ±90~110에서는 후보 0개 → Chase라 "옆·뒤 → 할퀴기↑"가 안 걸림) → 주말에 값 고칠 때 확인 |

- 인간성: 원래 11/01 "시간 되면"이었는데 새 일정에서 빠져 있었음 → **10/31 보상·소재 때** 넣음.

### 6. 단계 설계 다시 정하기 (1단계 · 2단계 · 공중)

계기: 가중치·후속타를 하려는데 1단계 패턴이 적어서 가중치 의미가 없어 보임 → 공중 패턴을 만들면 2단계가 애매해짐 → 2단계에 할퀴기 + 화염 상태는 다른 점이 별로 없음. 그리고 뒤에 있을 때 꼬리치기, `StrafeLeft`로 철산고.

**지금 패턴 (Variant Decide 목록)**
| 패턴 | 거리 | 각도 |
|---|---|---|
| 할퀴기 / 할퀴기 오른쪽 | 2~10 | +45~+90 / −90~−45 |
| 2연타 콤보 | 2~10 | −45~+45 |
| 물기 | 2~10 | −40~+40 |
| 점프 물기 | 8~15 | −40~+40 |
| 브레스 | 15~20 | −40~+40 |
| 제자리 돌기 좌/우 | 0~20 | ±110~180 |
- 불덩이는 Decide에 없음 (F 키만). 후보 0개 → Chase: ±90~110, **2m 안쪽 전부**, 20m 밖.

**모션**
- 꼬리 공격 클립 **없음** → `Turn90_RM` 빠르게 + 꼬리 히트박스 (몸을 홱 돌리면 꼬리가 휩쓸음, 몬헌의 몸 돌리며 꼬리 치기). 제자리 돌기와 같은 클립 → 속도·소리로 구분 필요 (내려찍기를 지운 이유와 겹치는 점 주의).
- 철산고: `StrafeLeft/Right_RM` 30프레임 → 빠르게 + 몸통 옆 히트박스. "간보기 안 함"은 어슬렁거리지 않는다는 뜻이라 한 번 치고 멈추는 공격과 안 부딪힘.
- 비행: `TakeOffToGlide`, `Glide`, `FlyNormal`, `FlyStationary`, `FlyStationarySpitFireBall/SpreadFire`, `FlyStationaryToLanding`, `GlideToLanding`, 공중 피격·추락. 제자리 비행으로 바로 뜨는 이륙은 없음.

**목표**
- 1단계: 한 번에 못 깸. **3~4번 도전**하면 깸. 그동안 장비 강화를 어느 정도 하거나 새 무기를 만들 정도.
- 2단계: **완전히 높은 벽** → 계속 도전. 요리를 여기서 배우고, 장비 강화·인간성을 적극적으로.

**결정**
| 항목 | 선택지 | 결정 |
|---|---|---|
| 꼬리치기·철산고 | A) 1단계에 약하게 / B) 1단계 HP 절반부터 / C) 2단계로 | **1단계에 넣음** ✅. 안전지대(옆·뒤)가 없어야 한 번에 못 깸. 예비동작은 확실하게 |
| 2단계의 다른 점 | 공중 상태 / 분노(빨라짐·후속타·화염) / 할퀴기 + 화염 상태 | **불: 화염 상태 + 화염 장판 + 공중** ✅. 요리(불 피해 감소)가 답으로 보임 |
| 대장간 열리는 시점 | A) 첫 사망 / B) 처음부터 / C) 첫 처치(GDD 원안) | **A) 첫 사망** ✅. "죽음 → 강화 → 재도전"이 1단계 안에서 돎. C는 3~4번 도전 중 강화와 안 맞음 |

| 헷갈린 점 | 정리 |
|---|---|
| 꼬리치기·철산고를 넣으면 처음 하는 사람에게 너무 어렵지 않나 | 난이도는 패턴 **수**보다 ① 예비동작이 읽히는지 ② 위치마다 답이 몇 개인지 ③ 틈이 있는지. 넣어도 위치마다 답은 1~2개. 바뀌는 건 "옆·뒤 안전지대가 사라짐" → 1단계 3~4번 도전 목표와 맞음 |
| 패턴이 적으면 가중치가 의미 없나 | 지금은 옆·뒤 후보가 거의 없어서 그럼. 철산고(옆)·꼬리치기(뒤)가 들어오면 "옆·뒤에 붙으면 ~↑"가 쓸 곳이 생김 |

- GDD 반영: §5 1단계(전/후에 점프 물기·콤보·불덩이, 꼬리치기, 철산고, 1단계 목표), §5 2단계(다른 점 = 불 + 공중, 비행 모션, 목표), §7 성장의 리듬, §9 대장간 = 첫 사망.
- [ ] 공중 상태의 형태(패턴 하나 vs 떠 있는 상태 + 공중 Decide)는 아직
- [x] 새 일정에 넣기: 꼬리치기·철산고 = **오늘(금) 가중치 전** (가중치를 바로 옆·뒤 상황에 써 보려고), 공중·화염 장판 = 월요일 2단계

### 7. 철산고 (HipCheck) — 옆 패턴

요약: 플레이어가 용의 **옆**에 있을 때 쓰는 몸통 박치기. 진오우거처럼 **반대쪽으로 한 발 쓱 빠짐 → 감속하며 거의 멈춤(예비동작) → 플레이어 쪽으로 들이받음**. 상태 클래스는 **하나**(`HipCheckState`)이고, 왼쪽/오른쪽은 `AnimatorTrigger`가 그때그때 고름. 히트박스는 아직 없음.

#### 전체 흐름 (플레이어가 용의 오른쪽에 있을 때)

| 순서 | 어디서 | 무슨 일 |
|---|---|---|
| 1 | (임시) H 키 → `Boss.ChangeState(HipCheckState)` | 나중에 Decide 패턴 목록으로 |
| 2 | `ChangeState` 134줄이 `AnimatorTrigger`를 **읽는 순간** | `Dot(보스 right, 보스→플레이어 방향)` > 0 → `"HipCheckRight"` (`Enter`보다 먼저 불림) |
| 3 | `HipCheckState.Enter` | `currentSpeed` = 1 → `HipWaitSpeed` 1, `isWaiting` 끔, 시간 0 |
| 4 | Any State → 준비 칸 `StrafeLeft_Rig` (트리거 `HipCheckRight`) | `StrafeLeft_RM`을 1.3배 × `HipWaitSpeed`로 → **왼쪽으로 쓱 빠짐** (= 예비동작) |
| 5 | 준비 칸 0.5 `HitWait` 이벤트 → `ReceiveAnimEvent` | `isWaiting` 켬 (속도는 아직 1) |
| 6 | `HipCheckState.Update` 매 프레임 | `currentSpeed`를 `MoveTowards`로 1 → `waitSpeed`(0.1)까지 `slowDownTime`(0.2초) 동안 줄여 `SetFloat` → 감속하다 **거의 멈춤** |
| 7 | 멈춘 시간 ≥ `waitTime`(0.5초) | `SetTrigger("HipCheckGo")` |
| 8 | 준비 칸 → 공격 칸 `HipCheckRight` (트리거 `HipCheckGo`, Exit Time 없음, 0.1초) | `StrafeRight_RM` 1.5배 → **오른쪽(플레이어 쪽)으로 들이받음**. 공격 칸은 `HipWaitSpeed`를 안 써서 속도 정상 |
| 9 | `BossStates.Update` | 공격 칸의 **Tag `HipCheck`** = `animatorStateName` → 진행률 > 0.65 → Idle |
| 10 | `Exit` | `HipWaitSpeed` = 1 (도중에 끊겨도 다음에 멈춰 있지 않게) |

#### 고민한 것과 트레이드오프

**1. 왼쪽·오른쪽 나누기**
| 선택지 | 장점 | 단점 |
|---|---|---|
| A) 상태 두 개 (할퀴기 L/R 방식) | 코드 거의 없음 | 클래스·enum·트리거·칸 두 배 |
| **B) 상태 하나 + 트리거 고르기** ✅ | 만들 게 하나 | `AnimatorTrigger`가 고정값이 아님, 끝 검사 손봐야 함 |
- 고르는 곳: **`AnimatorTrigger` 안** ✅ (134줄에서 `Enter`보다 먼저 읽힘, `Boss.cs` 안 고침) vs `Enter`에서 직접 `SetTrigger`.
- 판별: `SignedAngle` 대신 **내적** ✅ (부호만 필요). `forward`가 아니라 **`right`**와 내적.

**2. 끝 검사 (칸이 두 개)**
| 선택지 | 장점 | 단점 |
|---|---|---|
| (a) 고른 쪽을 필드에 저장 | 애니메이터 안 건드림 | getter가 저장까지 함, Update override |
| **(b) Tag** ✅ | 한 줄. 할퀴기 L/R도 같은 방식으로 쓸 수 있음 | 칸마다 Tag 붙이기 |

**3. 예비동작**
| 선택지 | 장점 | 단점 |
|---|---|---|
| A) 클립 앞부분만 느리게 | 브레스 방식 그대로 | 클립 앞에 무게 싣는 동작이 있어야 함 |
| **B) 반대쪽으로 한 발 뺐다가 치기** ✅ | 몬헌 몸통 박치기 느낌 | 칸·화살표 두 배 |
| C) 정지 + 신호(소리·먼지) | 클립 상관없음 | 동작이 없음 |

**4. 빠진 뒤 잠깐 멈추기 (진오우거처럼)**
| 선택지 | 장점 | 단점 |
|---|---|---|
| A) 멈춤 칸(Idle 클립) 끼우기 | 코드 없음 | 칸 두 개 더, 자세가 Idle로 섞임 |
| **B) 준비 칸을 Speed Multiplier로 얼리기** ✅ | 빠진 자세 그대로 멈춤 | 시간 재는 코드 |
| C) 상태가 시간 재서 트리거 | 초 단위 조절 | 코드 가장 많음 |

**5. 멈춤 → 공격 넘어가기**: Exit Time ❌ → **트리거 `HipCheckGo`** ✅ (아래 개념 표 "남은 애니메이션").

**6. 얼음처럼 멈춤**: 0으로 뚝 → **`MoveTowards`로 감속해서 0.1** ✅ (공격 칸 섞는 시간 늘리기는 안 함: 공격이 늦어지고 흐릿해짐).
- 값 기준: 목표 속도 = 멈춘 0.5초 동안 몇 프레임 더 움직이나 (0.1 → 약 2프레임, 0.3이면 두 번째 발 시작). 감속 시간 = 0.05는 거의 뚝, 0.1~0.2는 브레이크 느낌, 0.3 이상은 멈춤이 짧게 느껴짐.

**7. 속도**: 공격 칸 1.5배 (1배는 치는 느낌이 약함), 준비 칸 1.3배.

### 8. 할퀴기 L/R → 상태 하나 (`ClawAttack`)

요약: 철산고와 같은 구조로 정리. `ClawAttackLeft` / `ClawAttackRight` 두 상태 → **`ClawAttack` 하나**가 내적으로 왼발/오른발 칸을 고름. 두 칸에 Tag `ClawsAttack`.

#### 전체 흐름 (플레이어가 보스 오른쪽 +45~90에 있을 때)

| 순서 | 어디서 | 무슨 일 |
|---|---|---|
| 1 | `DecideState` | 거리 2~10, 각도 +45~90 → 후보 `ClawAttackState` |
| 2 | `ChangeState` → `ClawAttack.AnimatorTrigger` | `Dot(보스 right, 보스→플레이어)` > 0 → `"ClawsAttackLeft"` |
| 3 | 애니메이터 | Any State → `ClawsAttackLeft` 칸 (Tag `ClawsAttack`) |
| 4 | `Attack.ReceiveAnimEvent` | `HitboxOn L_Hand` (칸마다 원래 이벤트 그대로) |
| 5 | `BossStates.Update` | Tag `ClawsAttack` = `animatorStateName` → 0.8 넘으면 Idle |

#### 바꾼 것

| 어디 | 전 | 후 |
|---|---|---|
| `States/ClawAttackLeft.cs` | 클래스 `ClawAttackLeft`, 트리거 고정 `"ClawsAttackLeft"` | **파일·`.meta` 이름 변경 → `ClawAttack.cs`** (GUID 유지 → Variant 컴포넌트 안 끊김). `AnimatorTrigger` get 블록에서 내적 |

#### 고민한 것

- **enum을 왜 안 지우나**: Decide 패턴 목록은 enum을 **숫자**로 저장 (`patternName: 7` 등). 중간 값(`ClawAttackRightState` = 6)을 지우면 그 뒤 값이 하나씩 밀려서 콤보·Turn·물기… 전부 다른 패턴이 됨 → 주석만.
- **삭제 순서**: 스크립트를 먼저 지우면 Variant 오브젝트에 "Missing Script"가 남음 → **오브젝트 먼저, 스크립트 나중**.
- **파일 이름 변경**: `.cs`와 `.meta`를 같이 바꾸면 GUID가 그대로라 붙어 있던 컴포넌트가 유지됨 (`MeleeAttack` → `Attack` 때와 같음). 클래스 이름도 파일 이름과 같게.
- **왼발/오른발 짝**: 원래 Decide 목록대로 보스 **오른쪽 → `ClawsAttackLeft`**, 왼쪽 → `ClawsAttackRight`. 이름만 보면 반대 같지만 지금까지 플레이하던 그대로 유지.

| 헷갈린 점 | 정리 |
|---|---|
| Decide에서 같은 상태를 두 줄로? | 맞음. 패턴 조건은 각도 범위를 **하나**(min~max)만 가짐. −90~+90 한 줄이면 정면(−45~+45)까지 덮음 → 양옆 두 줄, 이름은 둘 다 `ClawAttackState`. 실제 어느 발인지는 `AnimatorTrigger`가 정함 |

### 9. 뒤 패턴 정하기 (꼬리치기 → 뒤로 박치기)

- 처음 계획: 꼬리치기 = `Turn90Left/Right_RM` 빠르게 + 꼬리 히트박스.
- 꼬리로 치려면 **플레이어 반대쪽으로** 돌아야 함 (오른쪽 뒤에 있으면 왼쪽으로 돌아야 꼬리가 오른쪽을 쓸음). 90°만 돌면 끝날 때 등을 보임 / 90° + 90° = 180°면 다시 플레이어를 봄.
- **문제: Turn 클립은 몸만 돌고 꼬리가 안 휨** → 꼬리로 맞은 느낌이 안 남.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A) 다른 클립 (`RunTurn`, `WalkTurn`) | 가장 쌈 | 꼬리가 휘는지 미리보기로 확인해야 함 |
| B) Turn 클립 복제 → Animation 창에서 꼬리 회전 키 추가 | 원하는 모양 | 애니메이션 편집 처음이면 오래 걸림 |
| C) 코드로 `LateUpdate`에서 꼬리 뼈 휘기 | 값으로 조절 | 뼈 여러 개 다루는 새 코드 |
| **D) 꼬리치기 대신 뒤로 엉덩이 박치기** ✅ | 철산고와 같은 구조. `WalkBackwards_RM` 빠르게. 클립에 꼬리 움직임이 없어도 어색하지 않음 | 몬헌식 꼬리 휘두르기는 아님 |

- **다음 세션에서 D로 만들기** (철산고 7번 구조 참고: 상태 + Variant 오브젝트 + 애니메이터 칸 + 박스 히트박스 + Decide 뒤 각도).
- → 10번에서 D도 안 하기로 바꿈 (뒤 전용 공격 없음).

**4. 도는 동안 회전 코드**: `Attack`은 `Enter`부터 히트박스 전까지 플레이어 쪽으로 돌림 → 루트 모션 회전에 코드 회전이 **더해져서** 180°보다 많이 돎 → 첫 돌기 칸에서 `RotateOff`, 할퀴기 칸에서 `RotateOn`.

**5. 180° 클립**: 없음 (`Turn90`뿐) → 90° 칸 두 번.

#### 헷갈린 점

| 헷갈린 점 | 정리 |
|---|---|
| 옆에서도 돌기가 나오나 | 원래 Decide 목록에서 Turn은 **뒤 두 줄에만** 있었음. 옆(거리 10~15 등)에서 후보가 없으면 Chase로 감 |
| 왜 돌기 칸에는 Tag가 없나 | `BossStates.Update`는 "지금 칸이 내 칸(이름·Tag)이고 진행률 > Exit Time"일 때 끝냄. 돌기 칸에 Tag를 붙이면 첫 돌기 0.8에서 상태가 끝나 버림 → **마지막 할퀴기 칸에만** |
| 오른쪽으로 돌면 왼발? `ClawAttack`과 같은 짝 아닌가 | **처음 위치** 기준이면 같음 (오른쪽 → 왼발). **할퀼 때 위치** 기준이면 반대: `ClawAttack`은 할퀼 때 플레이어가 오른쪽, 뒤 돌아 할퀴기는 180° 돈 뒤라 플레이어가 왼쪽 앞. 맞는지는 테스트에서 "발이 플레이어 쪽으로 나가나"로 확인 |
| 그냥 도는 상태는 없앤 건가 | 아님. `TurnLeft/RightState` 스크립트·Variant 오브젝트·칸은 그대로. **Decide 목록에서만 빠져서** 지금은 안 나옴 |

#### 결정 (테스트 전)
- 할퀴기 발: **왼쪽으로 두 번 돌면 오른발(`ClawsAttackRight`, `R_Hand`), 오른쪽으로 두 번 돌면 왼발(`ClawsAttackLeft`, `L_Hand`)** → 위 칸 표와 반대로 클립·이벤트 parameter를 Unity에서 맞바꿈 (바꾼 뒤 `TurnClawState.cs` 주석도 고치기)

#### 남은 것 (뒤 돌아 할퀴기)

- [ ] 플레이 테스트: 180° 가까이 도는지, 할퀴기가 닿는지, 상태가 Idle로 돌아오는지
- [ ] 임시 값 정하기 (돌기 Speed, 두 화살표 Exit Time·섞는 시간)

### 11. 버그: IdleState인데 계속 걸어감 (`Walk` 트리거가 남음)

증상: 화면 위 표시는 `IdleState`인데 용이 루트 모션으로 계속 앞으로 걸어감.

| 순서 | 어디서 | 무슨 일 |
|---|---|---|
| 1 | `ChaseState` 들어옴 | `AnimatorTrigger` = `"Walk"` → `SetTrigger("Walk")` |
| 2 | 애니메이터 | 이미 `Walk_RM` 칸이면 Any State → `Walk_RM` 화살표가 **Can Transition To Self 꺼짐**이라 안 탐 → 트리거가 **쓰이지 않고 남음** |
| 3 | 공격 → 끝 → `IdleState` | `IdleState`는 트리거를 안 보냄. 애니메이터는 공격 칸 → IdleBreathe |
| 4 | IdleBreathe에 들어간 순간 | 남아 있던 `Walk`가 이제 탈 수 있음 → `Walk_RM`로 감 → **상태는 Idle, 애니는 걷기** |

| 선택지 | 장점 | 단점 |
|---|---|---|
| A) Walk 화살표 Can Transition To Self 켜기 | 설정 하나 | Chase에 다시 들어올 때마다 걷기가 처음부터 재시작 (끊김) |
| **B) `ChaseState.Exit`에서 `ResetTrigger("Walk")`** ✅ | 걷기가 안 끊김, 남은 트리거만 지움 | 코드 한 줄 |

- `ChaseState.cs`: `Exit` override 추가 → `animator.ResetTrigger("Walk")`.
- A를 테스트하느라 켰던 **Can Transition To Self는 다시 끄기** (B로 충분).

| 헷갈린 점 | 정리 |
|---|---|
| 상태 이름이 Idle인데 왜 걷나 | 상태(코드)와 칸(애니메이터)은 **트리거로만** 연결됨. Idle은 트리거를 안 보내서, 애니메이터는 화살표·남은 트리거를 따라 혼자 움직임 |
| 트리거는 언제 사라지나 | **화살표가 그 트리거로 넘어갈 때** 쓰이고 꺼짐. 안 쓰이면 계속 켜져 있다가 나중에 탈 수 있는 화살표가 생기면 그때 탐 → 그래서 `ResetTrigger`로 직접 지움 (철산고 `HipCheckGo`도 같은 이유) |

- **→ 진짜 원인은 12번 (`IsTag("")`)**. 위 `Walk` 트리거 이야기는 일어날 수 있는 일이지만 이번 증상의 원인은 아니었음. `ResetTrigger("Walk")`는 해가 없어서 그대로 둠.

### 12. 버그: Chase가 바로 Idle로 바뀜 (`IsTag("")`)

증상: 화면 위 표시에 `ChaseState`가 거의 안 뜨고 `IdleState`인데 용이 걸어감 (11번과 같은 증상).

원인: 철산고(7번) 때 `BossStates.Update` 56줄에 `IsTag(animatorStateName)`을 추가함. `ChaseState` / `DeathState` / `DecideState`는 Variant에서 Animator State Name이 **비어 있음("")** = "끝 검사 하지 마"라는 뜻. 그런데 Tag를 안 붙인 칸은 Tag가 ""라서 `IsTag("")`가 **Tag 없는 칸이면 전부 true**.

| 순서 | 어디서 | 무슨 일 |
|---|---|---|
| 1 | `DecideState` → `ChaseState` | `Walk` 트리거 → `Walk_RM` 칸 (Tag 없음) |
| 2 | `ChaseState.Update` → `BossStates.Update` 56줄 | `IsName("")` false, 그런데 `IsTag("")` **true** → "내 칸"으로 통과 |
| 3 | 58줄 | `normalizedTime > exitTime(0)` → true → `OnAnimationEnd` → `IdleState` |
| 4 | 애니메이터 | Idle은 트리거를 안 보냄 → `Walk_RM` 계속 → **화면엔 Idle, 애니는 걷기** |

- 같은 이유로 `DeathState`도 죽는 애니가 끝나면 Idle → Decide로 다시 패턴을 고를 수 있었음 (같이 고쳐짐).

| 선택지 | 방법 |
|---|---|
| A) 맨 위에서 빠지기 | `animatorStateName`이 비어 있으면 바로 `return` |
| **B) Tag 검사에만 조건** ✅ | 56줄을 두 줄로: `isMyTag` = 이름이 비어 있지 않음 **그리고** `IsTag(이름)` → `IsName(이름) == false && isMyTag == false`면 `return` |

- 확인: 멀리서 용이 걸어올 때 `ChaseState` 유지, 공격 끝나고 Idle에서 제자리에 섬.

#### `BossStates`의 역할 / `Update`가 하는 일 (헷갈렸던 개념)

- `BossStates` = 모든 보스 상태의 **부모 클래스**. 이름(`Name`), 애니 트리거(`AnimatorTrigger`), 시작·끝(`Enter` / `Exit`), 그리고 `Update` = "내 애니 끝났나?" 감시.
- **코드(상태)와 애니메이터(칸)는 따로 돈다.** `ChangeState`가 트리거로 애니를 **시작**시키지만, **언제 끝났는지**는 코드가 모름 → 매 프레임 애니메이터에게 물어보는 게 `BossStates.Update`.

| 순서 (물기, Animator State Name `Bite`, Exit Time 0.7) | 어디서 | 무슨 일 |
|---|---|---|
| 1 | `Decide` → `ChangeState(BiteState)` | `SetTrigger("Bite")`, `BiteState` 오브젝트 켜짐 → 이 상태의 `Update`가 매 프레임 돎 |
| 2 | 53줄 | 칸을 섞는 중이면 패스 |
| 3 | 56~57줄 | 지금 칸이 `Bite`(이름 또는 Tag)가 아니면 패스 (아직 도착 전) |
| 4 | 58줄 | 진행률 > 0.7 → `OnAnimationEnd()` |
| 5 | `OnAnimationEnd` | 기본은 `ChangeState(IdleState)` |

- Chase처럼 **애니가 끝나서 끝나는 게 아닌 상태**는 이름을 비워서 4번까지 안 가게 함 (Chase는 `CanAttack()`으로 끝남).

- **레퍼런스**: 다크소울 = 거리 구간별 기술 확률 (우리 Decide와 같은 구조), 에스트 마시면 반응("입력 읽기"). 몬헌 = 일정 시간 이상 멀리 있으면 돌진·원거리. 둘 다 "멀어지는 속도"보다 **거리 + 시간**에 가까움.

#### `DetectDistance` (`Boss/DetectDistance.cs`, 용 루트에 붙임)

| 필드 / 함수 | 하는 일 |
|---|---|
| `boss` | `Awake`에서 `GetComponent<Boss>()` (같은 오브젝트) → `boss.Player`로 플레이어 위치 |
| `lastDistance` | 지난 프레임 거리 |
| `currentFarTime` | 멀어진 누적 시간 (`farTime`의 짝, `idleTime` / `currentIdleTime`과 같은 이름 규칙) |
| `farTime` = 1.5 | 기준 시간 (인스펙터) |
| `IsPlayerMovingAway` (get 블록) | `currentFarTime >= farTime` |
| `Update` | 플레이어 없으면 끝 → 거리 → 늘었으면 `Min(farTime, 누적 + dt)`, 아니면 `Max(0, 누적 − dt)` → `lastDistance` 갱신 |
| `OnGUI` (**임시**) | 화면 위 두 번째 줄에 누적 시간 / 기준 / 결과. Decide 연결 확인 뒤 삭제 |

| 헷갈린 점 | 정리 |
|---|---|
| 이 컴포넌트를 Decide에서 쓰면 되나 | 맞음. 이 컴포넌트 = **재는 쪽**(항상 켜짐), `DecideState` = **읽는 쪽**(켜질 때 물어봄). `ChaseState`가 매 프레임 `CanAttack()`을 부르니까 `CanAttack`도 같은 결과를 봐야 함 |
| `IsPlayerFar` 이름 | 거리("멀다")로 읽힘 → **`IsPlayerMovingAway`** (20m 거리 조건과 안 헷갈리게) |
| `Mathf.Max`로 최대값 막기 | `Max(farTime, …)`는 **큰 쪽** → 첫 프레임부터 1.5 → 바로 true. 최대값을 막는 건 **`Min`** |
| `>` vs `>=` | 최대값이 `farTime`이면 `>`는 절대 true가 안 됨 → `>=` |
| `=>` 한 줄 vs get 블록 | 하는 일 같음. get 블록이 `return`이 보여서 덜 헷갈림 |

- 위 거리 방식으로 테스트 → 동작은 맞았지만 **Chase로 쫓길 때는 거리가 안 늚** (용도 다가와서) → 그대로 두기로 했다가, **방향키를 살짝만 틀어도 깎이는 문제**로 판정을 **내적 방식으로 다시 짬** (아래).

#### `DetectDistance` 다시 짜기 → 내적 방식

여기부터는 "할 일을 물어보면 답하고, 답한 대로 구현" 방식으로 진행.

| 고른 것 | 선택지 | 이유 |
|---|---|---|
| Chase 중에 안 걸리는 것 | **그대로** ✅ / 플레이어 움직임만 보기 | (처음엔) 쫓길 때는 어차피 못 떨어뜨림 |
| 살짝 틀어도 깎이는 문제 | 가만히 두는 구간 / 간격 비교 / 깎는 양 줄이기 / **내적** ✅ | 거리 대신 "플레이어가 용 반대쪽으로 움직이나"를 봄. 살짝 틀어도 각도 기준 안이면 도망. 쫓길 때도 걸림 (외적은 좌우·수직용이라 필요 없음) |
| "움직였다" 최소 속도 | 걷기도 / 뛰기만 | 처음 뛰기만(4) → **걷기도 포함 1.5**로 바꿈 (걷기 2, 뛰기 7) |
| 속도가 기준보다 작을 때 (멈춤 등) | 깎기 / **그대로 + 쓰면 초기화** ✅ | 한 번 도망친 기록이 남음. 불덩이를 고르면 0 → 도망 한 번 = 불덩이 한 번 |
| 뛰는데 방향이 기준 밖 (옆·용 쪽) | **천천히 깎기** ✅ / 바로 0 | |
| 초기화를 부르는 곳 | **Decide가 `farDistancePattern` 줄을 골랐을 때** ✅ / `FireBallState.Enter` | Decide에 `detect` 필드가 이미 있음. 다른 도망 패턴이 생겨도 같이 적용 |

| 필드 / 함수 | 하는 일 |
|---|---|
| `lastPosition` (Vector3) | 지난 프레임 플레이어 위치 (`lastDistance` 대신) |

#### 4-3. 부위 깨짐 알림 (C2) + 이번 판 보상 모으기

요약: `Boss`가 부위 깨짐을 `OnPartBroken(BossPart)` 이벤트 하나로 알리고, `HuntManager.HandlePartBroken`이 표에서 소재를 찾아 **이번 판 보상(`currentHuntReward`)에 모음**. 처치 보상도 같은 객체에 더하고, `Finish`(처치든 사망이든)에서 `GameData`에 **한 번** 더한 뒤 결과 패널로 보냄 → 부위 소재는 죽어도 받음.

| 순서 (앞발을 깸 → 처치) | 어디서 | 무슨 일 |
|---|---|---|
| 0 | `HuntManager.Start` / `OnEnable` | `rewardTable.Load()`, `partRewardTable.Load()` / `boss.OnPartBroken += HandlePartBroken`. `currentHuntReward`는 필드에서 `new` (씬을 열 때마다 새로) |
| 1 | `Boss.ApplyHit` | `part.IsBroken == false`면 `bool broke = part.ReduceDurability(피해)` |
| 2 | `BossPart.ReduceDurability` | 내구도 0 이하 → `BrokenPart()` (IsBroken = true) → `true` 돌려줌 |
| 3 | `Boss.ApplyHit` | `broke`면 `OnPartBroken?.Invoke(part)` (부위마다 한 판에 한 번) |
| 4 | `HuntManager.HandlePartBroken` | `partRewardTable.Get(currentStage, part.PartName)` → 줄마다 `currentHuntReward.materials[(int)row.Material] += row.Count` (1단계 앞발 = 화룡 비늘 +2) |
| 5 | 같은 곳 | `Random.value < PartBrokenHumanityChance`(0.1)면 인간성 +1 |
| 6 | 보스 HP 0 → `OnDeath` → `Finish(Killed)` | `GiveKillReward()`: 같은 `currentHuntReward`에 소울·비늘 등을 **`+=`** (앞발 비늘 2 + 처치 비늘 3~4 = 5~6) |
| 6' | 플레이어 사망 → `Finish(Died)` | 처치 보상 없음. 4~5번에서 모은 것만 남아 있음 |
| 7 | `Finish` | `currentHuntReward.AddTo(GameData.Current)` (더하는 곳은 여기 한 곳) |
| 8 | 같은 곳 | `OnHuntFinished?.Invoke(result, currentHuntReward)` → 결과 패널에 부위 소재까지 같이 나옴 |

- 마지막 한 방에 부위가 깨지면: `ApplyHit` 안에서 3번(부위 알림)이 `Dead()`보다 먼저라 소재가 처치 보상과 같이 들어감.
- `HandlePartBroken`은 `isFinished`면 무시 (결과가 난 뒤에 깨지는 것은 안 받음).

| 파일 | 바뀐 것 |
|---|---|
| `Boss/BossPart.cs` | `public string PartName => partName;`, `ReduceDurability`가 `bool` (이번에 깨졌으면 true) |
| `Boss/Boss.cs` | `public event Action<BossPart> OnPartBroken;`, `ApplyHit`에서 알림 |
| `Flow/HuntManager.cs` | `partRewardTable`, `currentHuntReward`, 구독·해제, `HandlePartBroken` (새), `GiveKillReward`는 `void` + `+=`, `AddTo`·로그는 `Finish`로 |
| `RewardTable.tsv` / `RewardValue.cs` | `PartBrokenHumanityChance` 열 (두 단계 0.1) |

| 고른 것 | 선택지 | 이유 |
|---|---|---|
| 깨짐 알림 (C2) | ① `BossPart` 이벤트 → `HuntManager`가 부위마다 구독 / **② `Boss`가 받아서 이벤트 하나로** ✅ / ③ `BrokenPart`에서 `GameData`에 바로 | `HuntManager`는 `Boss` 하나만 앎 (`OnDeath`와 같은 모양). 파괴 효과(경직·다운)도 `Boss`가 하니 같은 곳 |

### 5. 소울 (떨어뜨리기 + 사망 소울) — 진행 중

요약: 죽으면 가진 소울을 죽은 자리에 **떨어뜨리고**(`Progress.droppedSoul`), 지난번 것을 못 주웠으면 그 **절반**만 돌려받음. 그리고 **사망 소울**(처치 소울 × 준 피해 비율 × `DeathRatio`)을 받음.

| 파일 | 내용 |
|---|---|
| `Data/DroppedSoul.cs` | `amount`(0 = 없음), `x, y, z`(죽은 위치), `wasHuman` |
| `Data/Progress.cs` | `public DroppedSoul droppedSoul = new DroppedSoul();` (하나만, 또 죽으면 덮어씀) |
| `Flow/HuntManager.cs` | `DropSouls()`, `CalculateDeathSouls()` (새), `Finish`의 사망 쪽 |

| 순서 (가진 소울 500, 지난번 떨어진 300 못 주움, 보스 HP 절반에서 사망) | 어디서 | 무슨 일 |
|---|---|---|
| 1 | `Finish(Died)` → `DropSouls` | `oldAmount = droppedSoul.amount` → 300 |
| 2 | 같은 곳 | `droppedSoul` = 500, 죽은 위치(x, y, z), `wasHuman` false (사람 상태는 인간성 장). 가진 소울 0 → 지난번 300은 덮어써서 사라짐 |
| 3 | 같은 곳 | `currentHuntReward.souls += 300 / 2` → +150 |
| 4 | `Finish` → `CalculateDeathSouls` | `준 피해 비율 = 1 − 50 ÷ 100 = 0.5` → `400 × 0.5 × 0.6 = 120` (소수점 버림) → 돌려줌 |
| 5 | `Finish` | `currentHuntReward.souls += 120` → `AddTo` → 가진 소울 0 + 270 = **270**, 결과 패널 "소울 +270" |

- **순서 주의**: 3·4(돌려받는 소울)를 2(떨어뜨리기)보다 먼저 하면 그것까지 떨어뜨림 → `DropSouls`가 먼저, `AddTo`는 맨 끝.

| 고른 것 | 선택지 | 이유 |
|---|---|---|
| 떨어진 소울 모양 | a `Progress`에 필드 3개 / **b 작은 클래스 `DroppedSoul`** ✅ | 한 덩어리로 보이고 옮기기·지우기가 한 번에 (`HuntReward`와 같은 방식) |
| 위치 | `Vector3` / **`float x, y, z`** ✅ | Newtonsoft JSON이 `Vector3.normalized`를 끝없이 따라가 에러 (`Self referencing loop`). float면 저장하는 날 할 일 없음 |
| 꺼내기용 `Position` 프로퍼티 (`[JsonIgnore]`) | 넣음 / **안 넣음** ✅ | 쓰는 곳에서 `new Vector3(x, y, z)` |
| 이름 | `DroppedSoul`, `amount`, `wasHuman`, `droppedSoul` / 함수 `DropSouls`(처음 `DeathPenaltySouls` → 동사로 시작하게 추천), `CalculateDeathSouls`(값을 돌려줌, 더하기는 `Finish`) | |

| 헷갈린 점 | 정리 |
|---|---|
| `Vector3`를 넣으면 왜 저장이 안 되나 | Newtonsoft는 public 필드 + **public 프로퍼티**까지 저장. `normalized`도 `Vector3`라 그 안의 `normalized`를 또 따라감 → 끝없음. (`JsonUtility`는 필드만이라 괜찮지만 `Progress`는 `Dictionary` 때문에 Newtonsoft) |
| `[JsonIgnore]` | "이건 저장하지 마" 표시. 프로퍼티로 `Vector3`를 돌려주면 그것도 저장하려 해서 붙여야 함 |
| 꺼내기용 프로퍼티가 뭐지 | 꺼내 쓰는 건 똑같고, 쓰는 곳마다 `new Vector3(drop.x, drop.y, drop.z)`를 쓰느냐, `DroppedSoul` 안에 한 줄로 두고 `drop.Position`으로 쓰느냐의 차이 |

- 진행 방식 추가: 새 함수·클래스는 **목표와 쓸 수 있는 값만 알려 주고, 순서(의사 코드)를 사용자가 먼저 씀** → 질문으로 짚고 → 쓴 대로 구현

### 6. 인간성 — 진행 중

| 순서 | 사용자 답 → 정리 |
|---|---|
| `Progress`에 새로 기억할 값? | "회복약 개수 int" → 최대 개수인가 남은 개수인가? → **최대 개수** (남은 개수는 `Awake`가 씬마다 채움) |

#### 6-3. 인간성 사용 (휠로 칸 고르고 R)

| 질문 | 사용자 답 → 정리 |
