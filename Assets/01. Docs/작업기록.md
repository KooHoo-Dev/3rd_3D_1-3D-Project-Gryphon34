### 1. 보스 AI

**DecideState: 거리 + 각도로 패턴 고르기**
- `Pattern`에 `minDistance / maxDistance / minAngle / maxAngle`
- 각도 = `Vector3.SignedAngle(보스 forward, 플레이어 방향(평면), Vector3.up)` → -180 ~ 180, **+ = 보스 오른쪽**
- `GetInfo(out distance, out angle)` 한 곳에서 계산. `IsInRange`는 private
- `CanAttack()`은 매개변수 없음. Chase는 "공격 가능한지"만 묻고, **결정은 전부 DecideState**에서
- 같은 패턴 2연속 금지: `lastState` 기억 → `patternList`(조건 맞음) → `tempPatternList`(지난번과 다름) → 비면 `patternList`로 연속 허용

**상태 추가**
| 파일 | 내용 |
|---|---|
| `RoarState` | 발견 프레임에 Idle → Roar. SpreadFire 클립, 끝나면 Decide |
| `MeleeAttack` (abstract, 전 `ClawAttack`) | `HitboxOn` 전까지 `RotateTowards`로 플레이어 추적. 애니 이벤트 parameter = `BossHitbox.id`인 히트박스만 켜고 끔 |
| `ClawAttackLeft / Right / ClawCombo / Bite / JumpBite` | `MeleeAttack` 자식. Bite는 제자리 클립이라 앞으로 안 나감(그냥 둠) |
| `TurnLeftState / TurnRightState` | Turn90 RM 클립, 끝나면 Decide. 등 뒤에 있을 때 제자리 돌기 |

**BossStates.Update**: `animator.IsInTransition(0)`이면 return. 같은 상태 재진입 때 이전 애니 정보를 읽는 문제 때문.

**규칙 (애니메이터 ↔ 코드)**
- 상태 컴포넌트 Exit Time < 애니메이터 "돌아가는 화살표" Exit Time. 안 지키면 상태에 갇힘
- 트리거 이름 = 코드 `AnimatorTrigger` / 애니메이터 칸 이름 = 인스펙터 Animator State Name / 오브젝트 이름은 자유
- 돌아가는 화살표는 "끝나고 코드가 트리거 없는 상태(Idle)로 갈 때만" 필요 (할퀴기·물기). Walk/Roar/Turn/Death는 불필요

**설계 결정 (GDD 미반영)**
- 간보기(Strafe) 안 함: 대검 차지를 하려면 보스가 멈춰 있는 틈이 필요
- 앞발 내려찍기 삭제: 할퀴기와 모션이 같아 헷갈림
- 1단계 공격은 전부 가드 가능
- 피로 상태: 앞발 공격 하다가 자빠짐

#### 고민한 것과 트레이드오프

**1. 각도 필드 모양**
| 선택지 | 장점 | 단점 |
|---|---|---|
| A) `maxAngle` 하나 (정면 기준 좌우 대칭) | 단순 | "등 뒤에서만" 같은 패턴을 표현 못 함 |
| **B) `minAngle` + `maxAngle`** ✅ | 거리와 같은 모양. 120~180처럼 뒤쪽 전용 패턴(꼬리치기)도 가능 | 필드 두 개 |

**2. Chase와 Decide의 "공격 가능" 기준 맞추기**
- 각도 필터를 넣자 `CanAttack(distance)`는 거리만 봐서, 사거리 안 등 뒤에 서면 Chase → Decide(후보 0개) → Chase가 매 프레임 반복됨.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A) `CanAttack(distance, angle)` — Chase가 계산해서 넘김 | 받은 숫자만 보니 시험하기 쉬움. Chase가 거리를 따로 쓸 일(멀면 뛰기)이 생기면 자연스러움 | "어떻게 재나"가 Chase·Decide 두 곳에 생김. 한쪽만 바꾸면 기준이 또 어긋남 |
| **B) `CanAttack()` — DecideState가 직접 계산** ✅ | 재는 방법과 판단이 한 파일에만. "결정은 전부 Decide" | Chase에서 거리·각도를 직접 못 봄 |
- A와 B 사이에서 흔들렸음. 기준: 방금 겪은 무한 반복이 바로 "기준이 두 곳에 있어서" 생긴 버그였다는 것.

**3. 겹치는 범위 검사를 어디로 모을까**
| 선택지 | 장점 | 단점 |
|---|---|---|
| **A) 패턴 하나를 검사하는 함수** ✅ | Enter와 CanAttack이 같은 조건을 씀 | foreach는 각자 남음 |
| B) 후보 목록을 돌려주는 함수 | foreach까지 하나로 | Chase가 매 프레임 리스트를 새로 만듦 |
- 함수 자리: `Pattern.IsInRange()`(카드가 스스로 답함) vs **DecideState의 private `IsInRange(pattern, …)`** ✅. Pattern은 값만 담는 상자로 두고 판단은 Decide가 함 → 2번 결정과 결이 맞음.

**4. 거리·각도 계산 모으기**
| 선택지 | 장점 | 단점 |
|---|---|---|
| A) `GetDistance()`, `GetAngle()` 두 개 | 단순 | 두 번 호출 |
| **B) `GetInfo(out distance, out angle)`** ✅ | 한 번 호출로 둘 다 | `out` 문법 |
| C) CanAttack이 구한 값을 필드에 저장하고 Enter가 재사용 | 계산 한 번 | Idle → Decide로 들어오면 **예전 값**이 남아 틀린 판단 |
- "모으기"는 계산을 한 번만 하는 게 아니라 **계산 코드를 한 곳에만 쓰는 것**.

**5. 왼쪽 / 오른쪽 구분**
- 옆발 할퀴기(보스 오른쪽 = 왼발, 보스 왼쪽 = 오른발, 정면 = 양발 콤보)를 넣으려고 `Vector3.Angle`(0~180, 좌우 구분 없음) → `Vector3.SignedAngle(…, Vector3.up)`(-180~180)으로 바꿈. 좌우 기준은 **보스 기준**.

**6. 옆구리에 붙으면 보스가 뺑글뺑글 도는 문제**
| 선택지 | 장점 | 단점 |
|---|---|---|
| A) 제자리 돌기 상태 (Turn90 RM 클립) | 도는 동작 자체가 공격 틈 (몬헌) | 상태·애니메이터 칸 추가, 좌우 고르기 필요 |
| B) 루트모션 없는 Walk + 코드로 이동 | "가까우면 멈추고 회전만"이 쉬움 | 발이 미끄러져 보임. 이동 코드 새로 |
| C) 옆발 할퀴기부터 | 옆구리 문제 대부분 해결 | 등 뒤는 남음 |
| D) 옆걸음(Strafe)으로 궤도 돌기 | 전진하지 않아서 플레이어를 지나치지 않음 | 사실상 간보기 행동 (7번) |
- 결론: **C + A** (옆은 옆발, 뒤는 제자리 돌기). GDD의 "옆·뒤에 붙으면 몸을 돌리며 할퀴기"와 같은 방향.
- `rotateSpeed`만 올리는 것도 해 봤지만 계속 돎 (어려웠던 개념 "걷기 + 회전 = 원").

**7. 간보기(Strafe)를 넣을까 — 패턴 느낌 정하기**
- 처음엔 "어떤 요소가 플레이어를 더 만족시킬까"로 보다가, **"이 보스 행동이 플레이어에게 무엇을 하게 만드나"**로 기준을 바꿈.

| 보스 행동 | 플레이어가 하게 되는 것 |
|---|---|
| 옆·뒤는 안전 (회전이 느림) | 위치를 잡고 파고들어 차지 |
| 옆에 오래 붙으면 회전 + 옆발 할퀴기 | 계속 붙지 않고 읽음. 태클·상쇄로 받아침 |
| 간보기 (옆걸음) | 기다리거나 다가감. 보스가 계속 움직여서 **차지가 어려움** |
| 거리 벌리기 (백스텝 + 불) | 붙어 있으면 손해라는 걸 배움 |
- 대검은 보스가 멈춘 틈에 차지해야 함 → **간보기 없음**. 간보기를 Decide 목록에 넣을지 Idle 확률로 할지, 도는 방향을 랜덤 / 플레이어 위치 / 플레이어 이동 방향(다크소울식) 중 무엇으로 할지도 고민했지만 함께 접음.

**8. 발견하고도 3초 기다리는 문제**
| 선택지 | 장점 | 단점 |
|---|---|---|
| A) 발견한 프레임에 바로 Decide | 가장 단순 | 연출 없음 |
| B) 발견 직후용 대기 시간을 따로 | 조절 가능 | 필드 추가 |
| **C) 포효 상태 (RoarState)** ✅ | "알아챘다"를 보여 줌 (몬헌) | 상태 추가. 포효 클립이 없어 SpreadFire 재사용 → 브레스와 시작 동작이 같아 헷갈릴 수 있음 (사운드·속도로 구분 예정) |
- 포효 뒤에는 브레스·점프 물기로 잇고 싶었지만 아직 상태가 없어서 **Roar → Decide** ✅. Roar에 다음 패턴 목록을 직접 두는 안은 거리·각도를 안 봐서 보류 (③ 후속타 분기 때 다시).
- 포효 `exitTime`: 미리보기에서 포효가 끝나고 자세가 돌아오기 시작하는 지점(88%) → 0.88.

**9. 각도 경계**
- 경계선 두 개(a = 정면/옆, b = 옆/뒤)만 정하면 다섯 패턴이 정해짐. 처음 a = 50, b = 90.

| 패턴 | 각도 |
|---|---|
| 콤보 | -50 ~ 50 |
| 왼발 | 50 ~ 90 |
| 오른발 | -90 ~ -50 |
| TurnRight | 90 ~ 180 |
| TurnLeft | -180 ~ -90 |
- 옆(40°)이 정면(100°)보다 좁은 게 걸림. 폭 계산: 정면 = `2a`, 옆 하나 = `b - a`. a를 줄이면 콤보 범위가, b를 늘리면 등 뒤가 좁아짐.
- 옆발을 40부터로 하고 싶음. 콤보를 -40~40으로 맞출지, -50~50으로 겹쳐 둘지(겹친 곳은 랜덤)는 **보류**.
- 범위 사이에 **구멍이 생기면** 후보 0개 → Chase → 뺑글뺑글. 경계는 맞닿거나 겹치게.
- "불편하지 않은 값"의 기준: ① 보이는 것과 맞는가(발이 실제로 닿는 범위), ② 안전지대 넓이(난이도). 차지할 틈을 위해 등 뒤는 넉넉하게.

**10. 범위를 어떻게 잴까**
- 할퀴기는 HitboxOn 전까지 추적 회전 → **Decide가 보는 각도 ≠ 실제로 맞는 각도**. 실제 범위 ≈ 클립이 쓸고 가는 범위 + 예비동작 동안 돈 각도(`rotationSpeed × HitboxOn까지 시간`).

| 선택지 | 장점 | 단점 |
|---|---|---|
| 한 패턴씩 각도를 바꿔 가며 맞는지 기록 | 정확. 추적 회전까지 포함 | 거리 × 각도마다 결과가 달라 끝이 없음 |
| **대략 넣고 이상한 순간만 고치기** ✅ | 빠름 | 정밀하지 않음 → 11/01 손맛 때 다듬기 |
- 서 있는 자리의 각도를 보려고 임시 OnGUI에 각도 표시 추가.

**11. Turn 거리**
- min 0: 꼬리 밑 2 안쪽이 어떤 패턴에도 안 걸리는 구멍이 되지 않게.
- max: 할퀴기(12)보다 작음 / 같음 / **큼(20)** ✅ — 멀리 있어도 먼저 제자리에서 돌고, 사거리 밖이면 그다음 Chase. 몬헌 몬스터가 돌아서서 다가오는 느낌.

**15. 히트박스를 id로 고르기**

**16. 같은 Turn이 연달아 나올 때**
- Can Transition To Self가 꺼져 있으면 애니가 다시 시작하지 않음 → 클립 끝 프레임에 멈춘 채 코드만 반복.
- 켜도 블렌드(0.25초) 동안 이전 Turn 정보(이미 exitTime을 넘음)를 읽어 바로 끝난 걸로 착각 → `BossStates.Update`에 `IsInTransition` 가드 ✅. 대가: "컴포넌트 Exit Time < 돌아가는 화살표 Exit Time" 규칙을 꼭 지켜야 함.

**17. 이름 짝을 어느 쪽에 맞출까 (Turn, Bite)**
- 트리거와 칸 이름이 다를 때 코드를 고칠지 애니메이터를 고칠지 → **애니메이터 칸 이름을 트리거와 같게** (`TurnRight`, `Bite`, `JumpBite`). 트리거·칸·인스펙터 이름이 같으면 짝을 헷갈릴 일이 줄어듦.

#### 어려웠던 개념

| 개념 | 헷갈린 점 | 정리 |
|---|---|---|
| `Vector3.Angle` vs Quaternion | Chase는 `FlatRotationTo`(Quaternion)를 쓰는데 Decide는 왜 `Vector3.Angle`? | Chase는 실제로 **돌려야** 해서 목표 회전값이 필요. Decide는 min/max와 비교할 **숫자 하나**면 됨 |
| `Vector3.Angle` 범위 | 최대 90이면 정면 90° 안? | 좌우 구분이 없어서 0~90 = 왼쪽 90° + 오른쪽 90° = **앞쪽 반원 전체** |
| `SignedAngle`의 축 | Z축 아닌가? | 축 = 꽂고 도는 막대. 바닥에서 좌우로 트는 건 **Y(`Vector3.up`)**. Z로 돌면 옆으로 구름 |
| `CanAttack` vs `IsInRange` | 같은 함수 아닌가 | IsInRange = 카드 **한 장** 검사, CanAttack = 손패 **전체** 중 한 장이라도 되나 |
| 거리·각도를 두 번 계산 | 한 번 구해서 다 넘기면 안 되나 | Decide로 오는 길이 둘(Idle, Chase). Idle 길에는 미리 구한 값이 없음. 같은 프레임 두 번 계산은 비용 거의 없음 |
| `ChangeState` 다음 줄 | 부르면 바로 Exit로 끝나는 줄 앎 | 평범한 함수 호출이라 끝나면 **다음 줄로 돌아옴**. `SetActive(false)`도 이번 Update를 끊지 않음 → 바꾼 뒤 `return` |
| `exitTime` | 정확히 뭔지 | 직접 만든 필드. 애니 `normalizedTime`(재생 비율 0~1)이 넘으면 `OnAnimationEnd`. 미리보기 % = 이 값. Loop 클립은 1, 2, 3…으로 계속 커짐 |
| enum 추가 위치 | — | 인스펙터의 enum은 **숫자 순서**로 저장 → 중간에 넣으면 저장된 값이 밀림. 항상 맨 끝에. 필드 기본값은 0번(`IdleState`) |
| 프리팹 Original / Variant / 씬 | Variant를 고쳤는데 씬이 안 바뀜 | Original → Variant → 씬 순서로 물려받고 **아래 단계에서 덮어쓴 값이 이김**. 굵은 글씨 + 파란 줄 = 오버라이드, 오른쪽 클릭 Revert로 지움 |
| 이름 세 종류 | 인스펙터 Animator State Name에 트리거 이름을 넣음 | 트리거 = 코드 `AnimatorTrigger`, 칸 이름 = Animator State Name, 오브젝트 이름은 자유 |
| 걷기 + 회전 = 원 | `rotateSpeed`를 올려도 계속 돎 | 전진하면서 돌면 원을 그림(회전 반경 ≈ 걷는 속도 ÷ 회전 속도). 원 안쪽 옆구리는 정면으로 못 들어옴 |
| 추적 회전과 범위 | 클립이 닿는 만큼 범위를 어떻게 잡나 | HitboxOn 전까지 돌기 때문에 판단 각도와 맞는 각도가 다름 |
| Hurtbox와 Hitbox 자리 | 턱뼈에 이미 Hurtbox가 있는데 어디에? | 같은 오브젝트면 히트박스를 끌 때(`SetActive`) Hurtbox도 꺼짐 → 턱뼈 밑 **형제** 오브젝트(같은 부모, 같은 들여쓰기)로 |
| 상속이 어색함 | 물기가 ClawAttack을 상속? | 하는 일은 근접 공격 공통이라 맞음. 어색한 건 **이름** → MeleeAttack |
| 목록 하나 더 | `patternList`를 새로 만들라는 건지 | `patternList`는 그대로 두고 `tempPatternList`를 **하나 더**. 지난번과 다른 것만 모으고, 비면 원래 목록에서 뽑음 |

### 2. 플레이어 피격 모션

#### 전체 흐름

| 순서 | 어디서 | 무슨 일 |
|---|---|---|
| 1 | 보스 히트박스 인스펙터 | 히트박스마다 `Reaction`(Small / Big / KnockDown)을 고름 |
| 2 | `BossHitbox.OnTriggerEnter` | 플레이어에 닿으면 `new AttackInfo(damage, fatigue, pos, reaction)` |
| 3 | `PlayerHealth.TakeDamage` | 무적이면 무시 → 체력 깎음 → 죽으면 `Die` 후 return → 아니면 `Reaction` int 설정 + `Hit` 트리거 |
| 4 | 애니메이터 Any State | `Hit` + `Reaction == 0/1/2` → Small / Big / KnockDown |
| 5 | `PlayerController.UpdateAnimState` | 칸의 Tag를 읽어 상태 클래스 실행. `Hit` → HitState, `Down` → KnockDownState |
| 6 | HitState / KnockDownState | 이동 즉시 멈춤. LocomotionState가 안 돌아서 이동·공격·구르기 입력 무시 |

넉다운은 6~7 사이에 KnockDown → Down(누워 있기 루프) → StandUp(일어나기)를 거치고, 그동안 무적입니다.

#### 고민한 것과 트레이드오프

결정마다 어떤 선택지가 있었고, 무엇을 얻고 무엇을 포기했는지 정리합니다.

**1. 반응 종류를 애니메이터에 어떻게 넘길까**
| 선택지 | 장점 | 단점 |
|---|---|---|
| 트리거 3개 (반응마다 하나) | 화살표 조건이 트리거 하나로 단순 | 파라미터가 반응 수만큼 늘어남. 코드에서 반응별로 분기해야 함 |
| **트리거 1개 + int 1개** ✅ | 파라미터 2개로 고정. enum을 `(int)`로 그대로 넘겨서 코드에 분기가 없음 | 화살표마다 조건이 2개 (Hit + Reaction == n). enum 순서를 바꾸면 애니메이터 조건도 같이 바꿔야 함 |

**2. Big 피격 중에 또 Big을 맞으면 (Can Transition To Self)**
- Small은 바로 정함: 연타 맞으면 계속 움찔하는 게 자연스러움 → 켜기.
- **Big은 애매했음.** 켜면 연타 공격(양발 콤보 등)에 맞을 때마다 휘청임이 처음부터 다시 나오고, 끄면 두 번째 타격은 데미지만 들어가서 "맞았는데 안 맞은 것처럼" 보임.
- 기준을 몬헌에서 가져옴: 새 타격이 앞의 반응을 덮어씀 → **켜기**. 대가로 연타에 갇힐 수 있는데, 그건 회피기(구르기)로 빠져나오는 구조로 받아들임.
- KnockDown은 켜도 꺼도 문제가 있었음 (켜면 누워서 또 쓰러짐, 끄면 트리거가 남아 일어나자마자 또 쓰러짐). 화살표 설정으로 풀 문제가 아니라 **"쓰러져 있을 때 맞으면?"이라는 설계 문제**라고 보고 **넉다운 무적**으로 해결.

**3. Transition Duration**
- 0이면 반응은 즉각이지만 자세가 툭 끊겨 튐. 길면 부드럽지만 "맞았다"는 느낌이 늦게 옴.
- Any State에서 오는 화살표는 앞 모션이 매번 달라서, 비율이 아니라 **Fixed Duration(초)**으로 정함. 일단 0.2초, 손맛 볼 때 다시 조정.

**4. 넉다운을 한 칸으로 할까, 세 칸으로 나눌까**
- 클립이 쓰러짐 / 누워 있기(Loop) / 일어나기로 나뉘어 있어서 **세 칸 다 씀**. 대가로 "누워 있다가 언제 일어나는가"를 따로 정해야 했음.

**5. 언제 일어날까**
| 선택지 | 장점 | 단점 |
|---|---|---|
| A) 애니메이터 Exit Time만 | 코드 필요 없음 | 플레이어가 개입할 수 없음 |
| B) 코드가 시간 재기 | 시간을 인스펙터에서 조절 | 역시 플레이어가 개입할 수 없음 |
| C) 입력으로 일어나기 | 몬헌처럼 빨리 일어나기 가능 | 입력을 안 하면 영원히 누워 있음 |
| **C + 자동 기상** ✅ | 둘의 장점을 합침 | 화살표 2개 (트리거 / Exit Time 3) + 트리거가 남지 않게 하는 조건이 필요 |
- 자동 기상 시간은 루프 1 / 2 / 3바퀴 중 **3바퀴**.
- 입력은 이동 / 구르기 / 둘 다 중 **둘 다**.

**6. 일어나기 클립**
- 같은 시리즈의 구르며 일어나기(`KnockDown_Front_BW/FW_Rolling_StandUp`)와 다른 폴더의 그냥 일어나기(`Damage_Front_Down_StandUp`) 중 **그냥 일어나기**를 고름.
- 대가: 시리즈가 달라서 시작 자세나 import 설정이 안 맞을 위험이 있었음 → 실제로 Root Y 설정 문제가 생겼고, 세 클립 import 설정을 통일해서 해결 (트러블슈팅 4, 5).

**7. 맞는 순간 이동을 바로 끊을까, 감속할까 (`StopMovement(true / false)`)**
- 몬헌·다크소울은 패드로만 해 봐서 감각으로는 판단이 안 됐음 → 레퍼런스 동작을 기준으로 정함.
- 몬헌·다크소울은 **입력 이동은 즉시 끊기고, 밀려나는 건 피격 모션이 함** → `true`.
- 대가: 지금은 클립의 XZ 루트 모션을 버리고 있어서(`OnAnimatorMove`는 구르기만 적용) **제자리에서 맞음**. 밀려나기는 손맛 단계로 미룸.

**8. 넉다운 무적을 어떻게 구분할까**
| 선택지 | 장점 | 단점 |
|---|---|---|
| A) 칸 이름으로 (`IsName`) | 애니메이터를 안 건드림. 파일이 안 늘어남 | 칸 이름이 코드에 박힘. HitState 하나가 두 역할을 함 |
| **B) Tag 분리 + KnockDownState** ✅ | 역할이 깔끔: HitState = 움찔, KnockDownState = 무적 + 일어나기 | 파일 하나 추가. 애니메이터 Tag를 바꿔야 함 |
- B를 골랐지만 KnockDownState 안에서 "Down 칸일 때만 입력 받기"는 결국 `IsName("Down")`을 씀. Tag로 큰 구분을 하고, 세부 구분은 칸 이름으로 하는 절충.

**9. 보스 공격이 안 닿음: 용 크기를 줄일까, 거리를 줄일까**
| 선택지 | 장점 | 단점 |
|---|---|---|
| A) 용 크기 + 패턴 거리 같이 줄이기 | 화면에서 보스가 덜 가림 | 패턴 거리·`discoverDistance`를 전부 다시 맞춰야 함. 크기만 줄이면 오히려 더 헛침 |
| B) 크기 그대로, 패턴 `maxDistance`만 줄이기 | 숫자만 고치면 됨 | 보스가 더 가까이 붙어서 공격함 |
- **결정 보류**. 피격 모션을 먼저 끝내기로 함.

**10. 테스트 방법**
- 인스펙터 ContextMenu(Test Player Hit)는 누르는 순간 Game 뷰 포커스가 빠져서 **달리면서 테스트할 수 없음**.
- 보스한테 맞아서 테스트하려 했지만 공격이 안 닿음 (9번).
- → **임시 키(1 / 2 / 3)**로 반응별 피격을 직접 발생시킴. 데미지는 0으로 해서 여러 번 눌러도 안 죽게 함. 테스트 후 삭제.

**11. 마우스 감도**
- 패드로만 해 봐서 마우스 기준이 없었음 → **"손목 한 번에 90~180도"**라는 동작 기준을 정하고, 보스 주위를 돌면서 보스를 화면 가운데에 둘 수 있는지로 맞춤.

**12. 피격 모션 개수**
| 선택지 | 장점 | 단점 |
|---|---|---|
| A) Small 하나 | 가장 빠름 | 모든 피격이 같은 모션 |
| B) 피해량으로 Small / Big | 큰 공격이 달라 보임 | 트리거나 칸이 늘어남 |
| **C) Small / Big / KnockDown** ✅ | 큰 공격에는 넘어짐 | 일어나는 동안 무방비 시간까지 정해야 함 (→ 4, 5, 8번) |

**13. 반응 종류를 누가 정할까**
| 선택지 | 장점 | 단점 |
|---|---|---|
| A) 피해량으로 (`PlayerHealth`가 정함) | 보스 쪽 코드는 그대로 | 방어구로 피해가 줄면 같은 공격인데 모션이 바뀜 |
| **B) 공격 쪽에서 (`BossHitbox` 인스펙터)** ✅ | 패턴마다 고정(할퀴기 Small, 물기 Big). GDD 구현 메모의 "`AttackInfo`에 태그 필요"와 같은 자리라 가드 불가·화염 태그도 나중에 붙일 수 있음 | `AttackInfo` 생성자가 바뀜 → 기본값으로 다른 호출부는 그대로 |
- enum 이름: `HitState`는 곧 만들 피격 상태 클래스(`DodgeState`, `DrinkState`처럼) 이름과 겹쳐서 **`HitReaction`**.

#### 어려웠던 개념

| 개념 | 헷갈린 점 | 정리 |
|---|---|---|
| `SetInteger(해시, 값)` | 인자가 하나뿐이면 에러, 순서를 바꾸면 에러 없이 무시 | 첫 번째 = **어느 파라미터**, 두 번째 = **무슨 값**. 둘 다 int라 컴파일러가 못 잡음 |
| 이름 비슷한 해시 두 개 | `HitHash`(Trigger)와 `ReactionHash`(Int)를 서로 바꿔 씀 | 해시 이름 = 애니메이터 파라미터 이름. 파라미터 **타입**이 맞는지 같이 확인 |
| 트리거가 안 꺼짐 | 버그인 줄 알았음 | 트리거는 **화살표가 가져갈 때** 꺼짐. 가져갈 화살표가 없으면 켜진 채 남음 |
| Sub-State Machine의 Entry 화살표 | 지울 수 없음 | 묶음의 기본 칸 표시. Any State에서 칸으로 바로 가면 안 거침 |
| Transition Duration | 뭐였는지 기억 안 남 | 앞 모션과 새 모션을 **섞는 시간**. Fixed Duration이면 초 단위 |
| Root Transform 설정 | 같은 시리즈 클립인데 튀고, 뜨고, 바닥을 뚫음 | Bake 안 하면 움직임이 루트 모션으로 빠지는데, 이 프로젝트는 구르기 외에 루트 모션을 버림 → 회전·높이는 **Bake + Original** |
| 용 크기와 거리 | 용이 커서 안 맞는다고 생각함 | 크기는 콜라이더·루트 모션과 같이 줄지만, 패턴 거리 같은 **월드 숫자는 안 줄어듦** |

#### 트러블슈팅

1. **`SetInteger` 인자 순서를 바꿔도 컴파일됨**
   `SetInteger(해시, 값)`인데 둘 다 int라 바꿔 써도 에러가 없음 → 없는 파라미터에 값을 넣어 아무 일도 안 일어남. 해시 이름(`HitHash`/`ReactionHash`)도 서로 바뀌어 있었음. **조용히 무시되는 버그**라 눈으로 확인해야 함.

2. **트리거가 안 꺼짐**
   트리거는 **그 트리거를 조건으로 쓰는 화살표가 넘어갈 때** 꺼짐. 화살표가 없으면 켜진 채로 남음. 반대로, 쓸 때가 아닌데 걸어 두면 나중에 엉뚱한 순간 발동함("남은 쪽지" 문제). → KnockDownState는 **Down 칸일 때만** `StandUp`을 걸게 함 (`stateInfo.IsName("Down")`). 일어나는 중에 걸면 다음 넉다운 때 눕자마자 일어나 버림.

3. **Sub-State Machine의 Entry → Small 화살표가 안 지워짐**
   묶음의 기본 칸(주황색) 표시라 지울 수 없음. Any State에서 칸으로 **바로** 꽂으면 Entry를 안 거쳐서 영향 없음.

4. **KnockDown → Down에서 몸이 튐 (회전)**
   Loop Time을 켜면서 Loop 클립의 import 설정이 기본값(Root Rotation = Body Orientation, Bake 꺼짐)으로 생김. 누워 있으면 "몸통 방향"이 위나 옆을 가리켜서 Unity가 몸을 돌려 맞춤. → 세 클립 모두 Rotation **Bake + Original**로 통일.

5. **KnockDown은 공중에 뜨고, StandUp은 다리가 바닥을 뚫음 (높이)**
   Root Position Y를 Bake 안 하면 위아래 움직임이 루트 모션으로 빠짐. 그런데 `PlayerController.OnAnimatorMove`는 **구르기일 때만** `deltaPosition`을 적용하고 나머지는 버림 → 쓰러지며 내려가는 움직임 / 일어나며 올라가는 움직임이 사라짐. → Y **Bake + Original**.

6. **보스 공격이 안 맞음**
   레이어는 정상 (히트박스 mask = PlayerHurtbox, 플레이어 레이어 = PlayerHurtbox, 충돌 매트릭스 켜짐). 일시정지 후 Scene 뷰로 보니 히트박스가 "닿을락 말락" → **휘두르기 시작 거리(패턴 maxDistance)가 용 팔 길이보다 멂**. 용 크기를 줄여도 패턴 거리·`discoverDistance`는 월드 값이라 같이 안 줄어듦 → 줄이면 오히려 더 헛침. **미해결 (나중에)**.

7. **애니메이터를 파일(YAML)로 고칠 때 주의**
   Unity에서 저장 안 한 애니메이터 변경이 있으면, 파일을 바꾸는 순간 Unity가 다시 읽으면서 그 변경이 날아갈 수 있음 → 저장 안 된 상태에서는 에디터 스크립트(Unity 안에서 열린 에셋을 직접 수정)로 작업.

#### 기타

- 테스트용 임시 1/2/3 키 → 테스트 후 `Update`는 삭제함.
