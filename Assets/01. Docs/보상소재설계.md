# 보상 · 소재 · 소울 · 인간성 설계 준비 (10/31 토)

토요일 계획 "부위파괴 나머지 → 보상(소재)·소울 드랍 + 인간성"을 시작하기 전에 읽는 문서입니다.
**정할 것은 전부 선택지만 적었습니다.** 값과 설계는 직접 고릅니다. 코드 위치는 10/30 작업 중인 파일 기준입니다.

읽는 순서: 0장(공통 전제) → 기능 하나 고르기 → 그 장의 "순서표"와 "정할 것" → "만드는 순서"를 한 조각씩.

## 0. 공통 전제: 씬을 넘어 남는 값

네 기능 모두 **"투기장에서 생긴 값이 마을까지, 다음 사냥까지 남아야"** 합니다. 그래서 이것부터 정해야 나머지가 움직입니다.

### 지금 코드

| 있는 것 | 위치 |
|---|---|
| 씬을 넘어 남는 값은 **딱 하나**: `public static HuntResult LastResult` | `Flow/HuntManager.cs:18` |
| 마을에서 그 값을 읽음 (`switch (HuntManager.LastResult)`) | `Flow/Bonfire.cs:11` |
| 플레이어는 **씬마다 따로** 있음: `00. Village`, `01. Boss` 둘 다 `ModularCharacters` 프리팹을 갖고 있음 | 씬 파일 |
| 그래서 씬을 옮길 때마다 HP·회복약이 처음 값으로 돌아감 | `Player/PlayerHealth.cs:29`, `Player/PlayerPotion.cs:26` |

- 좋은 점: "마을에 돌아오면 회복약 자동 보충"(GDD §4)은 이 덕분에 **이미 되고 있음**.
- 문제: 소울·소재·인간성·사람 상태를 `PlayerHealth`나 `PlayerPotion` 안에 두면 **씬이 바뀔 때 사라짐**.
- 파일 저장(게임을 껐다 켜도 남는 것)은 없음.

### 정할 것 A: 이 값들을 어디에 둘까 — **[막음: 전부]**

| 선택지 | 장점 | 단점 |
|---|---|---|
| A1) `static` 클래스 (`LastResult`와 같은 방식) | 이미 써 본 방식. 어느 씬, 어느 `Awake`에서도 바로 읽힘 | 인스펙터에 안 보임 → 값 확인은 `Debug.Log`·HUD로 |
| A2) ScriptableObject 에셋 하나 | 인스펙터에서 값을 보고 고칠 수 있음 (테스트로 "소울 9999" 넣기 쉬움) | 에디터에서는 플레이 중 바뀐 값이 **플레이를 멈춰도 에셋에 남음** → 시작할 때 초기화 필요. 쓰는 스크립트마다 에셋을 꽂아야 함 |
| A3) `DontDestroyOnLoad` 매니저 오브젝트 | 플레이 중 Hierarchy의 DontDestroyOnLoad에서 인스펙터로 보임. 나중에 저장 함수 붙이기 좋음 | 마을로 돌아올 때 **같은 오브젝트가 또 생김** → "이미 있으면 새것을 지운다" 처리. 투기장 씬에서 바로 Play하면 없음 |

참고:
- A1: 지금 프로젝트 설정(Enter Play Mode Options의 Reload Domain 켜짐)에서는 Play를 누를 때마다 static 값이 초기화됩니다. 이 설정을 끄면 지난번 플레이 값이 남습니다.
- A3: `PlayerHealth.Awake`처럼 씬이 열릴 때 값을 읽는 쪽이 있어서, "매니저가 먼저 준비돼 있나" 순서를 신경 써야 합니다 (A1은 이 걱정이 없음).

```csharp
public static class GameData { public static int Souls; }   // A1 모양 (클래스 이름은 예시)
DontDestroyOnLoad(gameObject);                         // A3 핵심 한 줄
```

### 정할 것

**B1) 보상 수치를 어디에 적을까** — [막음: 처치 보상 2번 조각]

| 선택지 | 장점 | 단점 |
|---|---|---|
| `HuntManager` 인스펙터 필드 (소울, 비늘 최소·최대) | 제일 빠름. 토요일엔 1단계 하나뿐 | 월요일 2단계 때 필드가 두 벌 → 단계 고르는 `if` |
| `[Serializable]` 단계 보상 클래스를 `HuntManager`에 배열로 | 인스펙터에서 단계별 한 줄. 에셋 없음 | 단계 번호와 배열 칸 번호를 맞춰야 함 |
| 단계 데이터 ScriptableObject (HP·공격력·보상을 한 에셋에) | GDD §10 "보스 단계도 데이터로"와 같음. 2단계 = 에셋 하나 추가 | 토요일에 클래스·에셋이 하나 더 |

**B2) 보상을 언제 줄까**

| 선택지 | 장점 | 단점 |
|---|---|---|
| 결과가 난 순간 (`Finish`) | 지금 로그 자리 그대로. 투기장 값(보스 HP 등)을 바로 씀 | 보여주는 곳(마을)과 주는 곳이 다름 → "이번 판에 받은 것"을 따로 적어야 |

**B3) 받은 것을 어떻게 보여줄까** — 막지 않음

| 선택지 | 장점 | 단점 |

1. 저장소(A)에 **가진 소울** 칸 하나 → `Debug.Log`로 값 찍어 보기
2. 보상 소울 수치(B1) → `Finish`의 처치 쪽에서 더하기. "Test Boss Killed"로 시험 → 마을에서 값이 남아 있나 확인
3. 비늘 최소·최대 → `Random.Range`로 더하기 (2장 C1 정한 뒤)
4. 첫 처치 bool 하나 → 첫 처치면 인간성 +1 (4장 1번 조각 뒤), 2단계 해금 bool만 켜 두기
5. "이번 판에 받은 것" 칸 → `Bonfire.Start`의 `case Killed` 로그에 찍기

| 얻는 법 | 소재 |

| `BrokenPart()`에서 저장소에 바로 더하기 | 제일 짧음 | 보스가 플레이어 인벤토리를 앎. 인간성 10%·"이번 판에 받은 것"을 거기서 또 챙겨야 |

**C3) 부위별 소재 정보를 어디에 적을까** — [C1 다음]

| 선택지 | 장점 | 단점 |
|---|---|---|
| `BossPart` 인스펙터에 소재 종류 + 개수 | 부위를 보면 바로 보임 | 꼬리는 2종이라 배열 |
| `HuntManager`에 "부위 이름 → 소재" 표 | 보상 수치가 한 곳에 모임 | `partName` 글자를 맞춰야 함 (오타 위험) |

**C4) 체력 구간을 누가 확인할까**

| 선택지 | 장점 | 단점 |
|---|---|---|
| `Boss.ApplyHit` 안에서, HP를 깎은 직후 → 이벤트 | 맞은 순간 정확 | `Boss`가 또 커짐 |

**C5) 처치할 때 구간 비늘도 더하나** — 값 문제, 막지 않음

**C6) 어느 부위를 깰 수 있게 할까 ("부위파괴 나머지")** — [막음: 소재 2번 조각의 값 입력]

| 선택지 | 장점 | 단점 |
|---|---|---|
| GDD대로 머리(뿔)·꼬리만 | 소재 표·무기 갈래("뿔을 노린다")가 그대로 | `Tail` canBroken 켜기, 머리 부위 확인. 앞발은 파괴 불가로 |

### GDD 규칙 (§6 죽었을 때)

1. 이번 판에 **준 피해 비율만큼 소울** (처치 보상의 최대 60%)
2. 부위파괴·체력 구간 소재도 받음 (2장)
3. **들고 있던 소울**(= 투기장에 들어갈 때 가진 소울)은 죽은 자리에 떨어짐
4. 사람 상태·식사 효과가 사라짐
5. 다음 판에 주우면 소울 + 마지막 사람 상태·식사가 돌아옴
6. 못 줍고 또 죽으면 떨어진 소울의 **절반은 화톳불로**, 나머지는 사라짐

### 순서표: 플레이어 HP 0 → 마을

| 순서 | 어디서 | 무슨 일 |
|---|---|---|
| 1 | `PlayerHealth.Dead` | `OnDeath?.Invoke()` |
| 2 | `HuntManager.PlayerDied` → `Finish(Died)` | (지금 로그 자리) |
| 3 | 같은 곳 (새) | 예전에 떨어진 소울이 아직 있나? → 그 양을 지역 변수에 잠깐 기억 (규칙 6용) |
| 4 | 같은 곳 (새) | 가진 소울 전부 → "떨어진 소울"로 옮김 (양, `player.transform.position`, 사람 상태였나). 예전 것은 덮어씀. 가진 소울 = 0, 사람 상태 끔 |
| 5 | 같은 곳 (새) | 3번에서 기억한 양의 **절반** + 준 피해 비율로 계산한 사망 소울(D1) → 가진 소울에 더함. 첫 사망 기록 |
| 6 | `ReturnToVillage` | 3초 뒤 마을 (그대로) |
| 7 | `Bonfire.Start` `case Died` | 첫 사망이면 "소울을 투기장에 두고 왔다" + 받은 소울 표시 |

- **4 → 5 순서 주의**: 5(돌려받는 절반, 이번에 번 소울)를 4보다 먼저 더하면 그 소울까지 떨어뜨리게 됨.
- 들고 온 소울이 0이면 떨어진 소울도 0 → 다음 판에 생성 안 함 (주울 것 없음).

|---|---|---|

| 2 | 떨어진 소울 오브젝트 `OnTriggerEnter` | `FogGate`처럼 `PlayerController`인지 확인 |

| 4 | 같은 곳 | 저장소의 떨어진 소울 지움 + 오브젝트 `Destroy` + 로그 |

### 정할 것

**D1) 죽었을 때 받는 소울 계산** — [막음: 소울 3번 조각. 값이라 나중에 바꾸기 쉬움]

| 선택지 | 장점 | 단점 |
|---|---|---|
| 처치 소울 × 준 피해 비율 × 0.6 (반 깎으면 120) | 계산 한 줄, 항상 60% 아래 | 거의 다 잡고 죽어도 240 |
| 처치 소울 × 준 피해 비율, 60%에서 자름 (반 깎으면 200) | 초반 피해가 더 보상됨 | 60% 넘게 깎은 뒤의 피해는 소울로 안 보임 |

- 참고 (1단계 400 기준): 철 대검 +1 = 소울 200. 첫 번째 안은 한 판에 **약 83%를 깎아야** 200, 두 번째 안은 **50%**. "3~4번 도전하며 강화"(10/30 결정)와 맞는 쪽을 고르기.

**D2) 떨어진 소울 오브젝트를 누가 만들까**

**D3) 같은 판에서 주운 뒤 또 죽으면**

| 선택지 | 장점 | 단점 |
|---|---|---|
| 주운 소울도 "가진 소울" → 새 자리에 다시 떨어짐 (다크소울) | "가진 소울은 떨어진다" 규칙 하나 | 회수하자마자 죽으면 아픔 |
| 주운 소울은 바로 안전 | 덜 가혹 | 회수 긴장이 줄고 예외 규칙이 생김 |

**D4) 처치했는데 지난 판 소울을 안 주웠으면**

| 선택지 | 장점 | 단점 |
|---|---|---|
| 그대로 남음 (다음 판에 주우러 감) | 규칙 변경 없음 | 처치 후에도 주우러 한 번 더 들어가야 |
| 처치하면 자동 회수 | 처치가 더 시원함 | 사람 상태 복구까지 자동인지 규칙이 하나 더 |

### 만드는 순서 (소울 드랍)

1. 저장소에 떨어진 소울 칸: 양(int), 위치(`Vector3`), 그때 사람이었나(bool)

| GDD 그대로 (첫 처치 1 + 부위파괴 10%) | 규칙 변경 없음. 처치가 큰 보상 | 1단계 3~4번 도전 동안 거의 0개 → 1단계에선 인간성 고민이 안 생김 |
| 부위별 **첫 파괴**에 확정 1 (그 뒤는 10%) | "꼬리를 노린다"에 이유가 하나 더 | 얻는 양이 늘어 회복약 5개가 빨리 참 |
| 첫 사망 때 1 (대장간과 같이 공개) | "죽음 → 강화" 루프에 인간성도 들어감 | GDD §9 공개 순서(첫 처치)와 달라짐 |

**E2) 언제 쓸 수 있게 할까**

| 선택지 | 장점 | 단점 |
|---|---|---|
| 화톳불 + 전투 중 (GDD) | 억까 패턴의 버틸 수단 (GDD §4) | 전투용 상태 + 입력 + 애니 이벤트까지 토요일에 |
| 토요일엔 화톳불만, 전투 중은 그 뒤 | 토요일 분량이 작음 | "버틸 수단"이 늦게 들어감 |

**E3) 최대 HP +25를 어떻게 붙일까** — [막음: 인간성 3번 조각]

| 선택지 | 장점 | 단점 |
|---|---|---|
| `PlayerHealth`가 사람 상태를 보고 `MaxHealth`에서 +25 | 가장 짧음 | 방어구·요리 때 또 다른 방식이 필요할 수 있음 |
| 보너스 숫자 칸 하나 (사람 상태가 +25를 넣고 뺌) | 방어구·요리도 같은 칸에 더할 수 있음 | 누가 언제 빼는지 관리 |
| GDD §10 "버프 목록의 합" | 요리·방어구·인간성 모두 "버프 하나 추가" | 클래스 + 리스트 → 토요일엔 큼 |

- 어느 쪽이든 `PlayerHealth.cs:29`, `:60`의 `maxHealth`도 같은 값(`MaxHealth`)을 쓰게 바꿔야 +25까지 채워짐.

**E4) 화톳불 상호작용 방식** — [막음: 태우기, 화톳불 사용]

| 선택지 | 장점 | 단점 |
|---|---|---|
| 트리거 안에서 [E] → 숫자 키 두 개(태우기 / 사용) + 로그 | UI 없이 금방 | 발표 때 알아보기 힘듦 → 안내 글자 한 줄은 필요 |
| [E] → 작은 UI 패널 (버튼 2개) | 일요일 대장간·냄비 메뉴와 같은 틀로 재사용 | 커서 켜고 끄기, 메뉴 동안 플레이어 입력 막기 |

**E5) 사람 상태에서 또 사용하면**

| 선택지 | 장점 | 단점 |
|---|---|---|
| 막음 | 낭비 방지 | — |
| 허용 (HP 전부 회복만, 최대 HP는 그대로) | "전회복 약"으로도 씀 | 회복약보다 훨씬 강해 태우기 고민이 줄 수 있음 |

**E6) 떨어진 소울을 주워 사람 상태가 돌아올 때 HP는**

| 선택지 | 장점 | 단점 |
|---|---|---|
| 최대 HP만 +25 (지금 HP 그대로) | 단순 | — |
| HP도 전부 회복 | 줍는 보상이 큼 | 확장의 "귀환의 호석"(회수 시 전회복)과 겹침 |

### 만드는 순서 (인간성)

1. 저장소에 인간성 개수 / 태운 수 / 사람 상태 칸 + 우클릭 메뉴 "인간성 +1" (테스트용)
2. `PlayerPotion.Awake`: 최대치 = 인스펙터 `maxCount`(기본 3) + 태운 수 → HUD "3/4" 확인
3. `PlayerHealth`: 사람 상태면 최대 HP +25 (E3), `:29`·`:60`도 같은 값으로
4. 화톳불 [E] 트리거 (E4) → 태우기
5. 화톳불에서 사용 → 투기장에 가서 HP 바가 길어졌나 확인
6. 죽을 때 사람 상태 끄기(3장 2번 조각) + 주울 때 켜기(3장 6번 조각). 전투 중 사용(E2)·HUD 인간성 칸은 그 뒤

## 6. 토요일 순서 제안 (기능 단위)

순서도 직접 정합니다. 아래는 "앞 기능이 뒤 기능의 저장소를 먼저 시험해 준다"는 기준의 한 가지 안입니다.

| 순서 | 기능 | 이유 |
|---|---|---|
| 1 | 0장 저장소 (A) + 1장 처치 보상 1·2번 조각 | 가장 작은 끝까지 한 바퀴: "Test Boss Killed" → 마을에서 소울 값이 남아 있나 |
